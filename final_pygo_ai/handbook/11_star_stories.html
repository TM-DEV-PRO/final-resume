11. STAR stories

How to use this page

  • It holds 15 real stories from my work, written so I can tell each one in about two minutes. Each story lists the questions it answers, the full Situation, Task, Action and Result, what I learned, the follow-ups I should expect, and an honesty note.
  • Read it before any behavioural, hiring-manager or "bar raiser" round. Before a loop, pick three stories from the question-to-story map and practise only those.
  • Memorise for each story: the one-line situation, the three key actions, the result number with its tag, and the one-sentence lesson. Paraphrase everything else.
  • Never tell the same story twice in one interview loop. This bank is big so you never have to.

What STAR means. STAR is the standard shape for behavioural answers: Situation (where and when), Task (what I had to achieve), Action (what I did), Result (what happened, ideally with a number). I add a fifth part, Lesson, because interviewers at senior level care most about what you would do differently.

Tags. MEASURED means there is a log, document or code behind the number. ESTIMATED means it is arithmetic I can show, so I say "roughly". HISTORICAL means it comes from my past work records. TARGET means it was a design goal, so I say "targeting". DESIGN means it was written but not executed. Untagged numbers are resume numbers, explained in Numbers explained.

Story 1. The 170 GB weekly rollup crash

Answers: biggest technical challenge · a time you hit a hard resource limit · dive deep · a setback or failure you recovered from · working within constraints. Project: Impact Analytics, AssortSmart ClickHouse rollups. Tags: 170 GB, one fiscal week per insert, memory and disk-spill caps are on the resume. 55 GB, 16 GB, 8 threads, 4 weeks in flight, 11 GB and 40 GB are verbal depth from the build settings and runs.

Words you need. - Rollup table. A table of pre-computed totals, for example sales per product per week, so planners read a small summary instead of summing billions of raw rows on every click. We have six: product, store and attribute, each at season grain and weekly grain. - INSERT SELECT. One SQL statement that reads rows with a query and writes the result into another table. Here it reads daily facts and writes weekly totals. - Aggregator state. The working memory a database keeps while grouping, like a running tally sheet per group. More groups and more columns mean a bigger tally sheet. - OOM (out of memory). The database kills the query because it needs more memory than it is allowed. - Disk spill. Letting the database write part of its tally sheet to disk when memory is full, slower but survivable.

Situation. Planners need weekly numbers, so we needed weekly rollup tables, not just season totals. The weekly build has to keep about 110 any() aggregate values plus argMax and argMin over wide text columns for every group. When I ran the build as one INSERT SELECT for a whole season, the aggregator state came to around 170 GB. It failed with MEMORY_LIMIT_EXCEEDED with an 80 GB cap, and failed again with a 200 GB cap. The replica had about 59 cores and about 236 GiB of memory, so "just give it more" had already run out of road.

Task. I had to keep weekly grain, because planners need fiscal-week numbers, without crashing the replica and without asking for bigger hardware.

Action. 1. After the second failure I stopped raising the memory cap. I measured the build per table grain (product, store, attribute) to find out which part was heavy. 2. I changed the unit of work from one season to one fiscal week. Each INSERT SELECT now builds a single week, so its tally sheet holds one week of groups instead of a whole season. 3. I generated the build settings per run: 8 threads, a 55 GB memory cap, 16 GB of disk spill, and at most 4 weeks in flight at once. 4. I measured real peaks. A product week peaked around 11 GB. An attribute week for the heaviest retailer peaked above 40 GB, so a 40 GB cap was too low for that table. Attribute tables are the heaviest because they "unpivot" each product into one row per attribute pair, which makes attribute weekly about 5x the size of product weekly. 5. I set one rule for the team: do not raise season parallelism and week parallelism at the same time on the same box, because the memory multiplies.

flowchart LR A["Before: one INSERT for a whole season"] --> B["About 170 GB of aggregator state"] B --> C["Killed at 80 GB cap and at 200 GB cap"] D["After: one INSERT per fiscal week"] --> E["Product week about 11 GB, attr week over 40 GB"] E --> F["Fits under 55 GB cap with 16 GB spill, 4 weeks in flight"]

What to notice: the fix did not add memory. It made each piece of work small enough to fit.

Result. Weekly-grain rollups build reliably. Planners read partition-pruned weekly tables. This is load-time work. The 15.5x pivot speed-up (189s to 12s) is a separate query-time result measured on a 250M-row harness, and I say that unprompted.

What I learned. Shrink the unit of work before you buy more memory. And measure the heaviest slice first, because the average week tells you nothing about the attribute week that kills the box.

Likely follow-ups. - "Why not just use a bigger machine?" "It already failed at a 200 GB cap on a 236 GiB box. Even a single attribute week needs over 40 GB, so a whole season would keep growing with the data. Week slicing makes memory bounded by the week, not the season, so it keeps working as data grows." - "Is this why pivots got 15.5x faster?" "No. That is a common mix-up. The OOM fix is about building the tables. The 15.5x is about reading them, measured on a separate 250-million-row harness. They're two different wins." - "Why are attribute tables so big?" "They unpivot. Each product row becomes one row per attribute pair using ARRAY JOIN, so attribute weekly is about five times product weekly." - "How do you know a week finished?" "From the server, not the client. I check system.query_log for the query's finish event, and a ledger records finished weeks. Story 2 covers why that matters."

Honesty note. Say this carefully: 170 GB is how much the full-season build needed, and the resume says I "prevented 170GB OOM crashes". The exact knobs (55 GB, 16 GB, 8 threads, 4 weeks) are verbal depth, fine to say if asked, not resume numbers. Never say the OOM fix caused the 15.5x speed-up.

Story 2. Copying billions of rows when the clusters could not talk

Answers: ownership · ambiguity and working around a constraint · bias for action · how you handle failure and idempotency · a bug in your own system. Project: Impact Analytics, ClickHouse Cloud migration. Tags: 344k rows/s, 4.09B, 500k-row double-buffered batches, TSV ledgers and partition rollbacks are on the resume. The two season streams of 150k to 190k rows/s and the 64.1M half-loaded partition are MEASURED verbal depth. The REPLACE PARTITION incremental pipeline is DESIGN only.

Words you need. - Partition. A slice of a table stored separately, here one slice per season (season_code). You can drop or rebuild one season without touching the others. Like one drawer per season in a filing cabinet. - IP allowlist. A firewall list of which addresses may connect. Our cloud clusters could not reach each other, but my operator machine was allowed to reach both. - Native TLS protocol. ClickHouse's own encrypted binary protocol (port 9440), faster than sending data over HTTP. - Double buffering. Using two buffers so you read the next batch while the previous one is still being sent. Like one person washing dishes while another dries. - Ghost rows. Rows from a load that crashed halfway. The partition "has rows", so it looks finished, but it is incomplete.

Situation. We needed to copy the rollup tables between two ClickHouse Cloud clusters. The normal approach, one cluster pulling directly from the other, was blocked by cross-cluster IP allowlists. The biggest object was the attribute weekly table for two seasons: 4.09 billion rows (2,779,317,472 plus 1,311,108,195). Before this, I had already been bitten by a related problem in my own weekly loader: a failed HTTP insert still committed some blocks, and a half-loaded partition of 64.1 million rows passed a "skip this season if it already has rows" check. So I knew partial loads that look complete were the real danger.

Task. Move billions of rows between clusters, make every run restartable, and make sure a crash could never leave ghost rows that look like a finished copy.

Action. 1. I wrote a Go data pump that connects to both clusters over the native TLS protocol from the allowlisted machine. It reads from the source and writes to the target, so no cluster-to-cluster connection is needed. 2. I made it fast. It works in 500,000-row columnar batches, appending whole columns at a time with no per-row reflection. Two buffer sets mean the read of the next 500k overlaps the send of the previous 500k. That overlap also fixed an "unexpected EOF" error I had seen when a read sat idle during a long insert over HTTP. 3. I made it restartable per season. Each table has a checkpoint file, migrate-checkpoints/<table>.done, listing finished seasons. If a season is not marked done but the target already has rows, the pump drops that partition and recopies it. On Ctrl-C it finishes the batch in flight and does not mark the season done. A per-table file lock stops two terminals copying the same table. It never retries a batch that has already been sent, because that creates duplicates. 4. I fixed the loader the same way. A TSV ledger records each finished (table kind, season) pair, and "finished" means system.query_log shows the query completed on the server, not that curl exited cleanly. A missing ledger entry means drop that season's partition and rebuild it. 5. I wrote down the honest limit. Dropping a partition and recopying is not an atomic swap, because readers can see a partial season during the rebuild. I wrote a safer incremental design that builds into a side table and swaps it in with REPLACE PARTITION. That design was written, not executed.

flowchart LR S["Source ClickHouse Cloud"] -->|native TLS SELECT of 500k rows| P["Go pump on allowlisted machine"] P -->|native TLS INSERT of 500k rows| T["Target ClickHouse Cloud"] P --> K["Checkpoint file per table, finished seasons only"]

What to notice: the pump sits in the middle because the clusters could not reach each other. The checkpoint only ever records whole finished seasons.

Result. The pump ran at about 344,000 rows per second combined, as two season streams of roughly 150,000 to 190,000 rows per second each, measured on the 4.09-billion-row attribute weekly set while that copy was in flight. Smaller tables and seasons completed and were checkpointed. Ghost rows from crashes are handled by the ledger and checkpoint rules instead of by hope.

What I learned. A crash must never look like success. Define "done" by what the server says finished, and make the unit of retry something you can safely throw away and redo.

Likely follow-ups. - "344k requests per second?" "No, rows per second of copy throughput. It's not an API." - "Did the 4.09-billion-row copy finish?" "I measured the rate on that set while it was in flight. I don't claim the cutover finished." - "Is your partition rollback atomic?" "No. It's drop the partition and recopy that season. A crash in between leaves a hole until the rebuild. The atomic version, build aside and REPLACE PARTITION, is designed but not run." - "Would you run production copies through a laptop?" "Not by choice. It was a workaround for the allowlists. With the right network access I'd use a direct INSERT SELECT between clusters or stage through object storage." - "Why Go?" "Native ClickHouse client with columnar batches, cheap concurrency for two season streams, and a single binary to run."

Honesty note. Say this carefully: 344k is rows per second, not requests or transactions. 4.09B was "measured on", not "migrated". The 64.1M half-loaded partition was the loader, not the copier. Never paste cluster hosts or passwords, and never offer to open-source the copier.

Story 3. Settling the ClickHouse debate with evidence

Answers: influence without authority · disagreement between teams or senior people · making a decision with incomplete data · what you are most proud of · taking initiative. Project: Impact Analytics, choosing the analytics database for planner reads. Tags: 189s to 12s on 250M rows and 15.5x are on the resume (MEASURED proof of concept, 12.3s rounded to 12s). The three-gate plan, the zero mutation queue at 10x scale and the July 2026 commitment are from my RFC and decision records.

Words you need. - OLAP (online analytical processing). Workloads that read and summarise lots of rows, like dashboards. The opposite of OLTP, which is many small reads and writes like "update this one order". - Mutation. ClickHouse's name for an UPDATE or DELETE. ClickHouse is built for appending data, so mutations rewrite whole chunks in the background and can pile up in a queue. - ReplacingMergeTree. A ClickHouse table type that keeps only the newest version of a row with the same key. Think of a notebook where you never erase. You write the new value below, and a cleaner later crosses out the old lines. - RFC (request for comments). A written design proposal that others review before anyone builds it. - Row-identical harness. The same rows and the same query run on both databases, with answers compared, so the comparison is fair.

Situation. Planner pivots on PostgreSQL were slow, past 30 seconds and up to 189 seconds at 250 million rows. The organisation was split on ClickHouse. A live audit of the legacy backend had concluded "no ClickHouse". Senior subject-matter experts wanted "yes, ClickHouse for everything". Both sides had real evidence, and a wrong call was expensive either way.

Task. Produce a recommendation the organisation could commit to, without throwing away either side's evidence. I could prototype on my own, but I could not commit the organisation on my own.

Action. 1. I separated facts from conclusions. I accepted every measured fact in the audit. Then I showed that its "no" conclusion came from the legacy system's write model, which updated rows in place, and ClickHouse is weak at in-place updates. It was not a verdict on analytical reads, which is what planners need. 2. I designed an insert-only, versioned write model using ReplacingMergeTree, so new values are appended as new versions instead of updated in place. That sidesteps the mutation weakness the audit had found. 3. I wrote the RFC and proposed a staged path with three measurable gates: fix what we could inside the existing BigQuery stack first, tighten Postgres usage second, and run a versioned-write proof of concept third. If a gate failed, we would stop. 4. I ran a row-identical proof of concept: the same 250 million rows and the same pivot on Postgres and ClickHouse, with answers compared. 5. I kept Postgres where it belongs: thin metadata, user access management and roles.

Result. Both camps agreed to the staged path. The proof of concept held the mutation queue at zero at 10x scale, and the pivot went from 189 seconds to 12 seconds, which is 15.5x faster. In July 2026 the organisation committed to ClickHouse for planning analytics. No premature infrastructure spend, and no camp "lost".

What I learned. When competent people disagree, it is usually about a hidden assumption, not about the facts. Make the assumption explicit and the decision often resolves itself.

Likely follow-ups. - "How did you avoid looking like you were picking a side?" "By starting with the audit's facts and agreeing with all of them in writing. I only challenged the step from the facts to the conclusion." - "Why not just tune Postgres?" "That was literally gate two. Postgres is great for transactional rows. Wide analytical pivots over hundreds of millions of rows are what column stores are built for, and the harness showed it." - "What does Postgres still do?" "Thin metadata, user access management and role resolution. ClickHouse handles large analytical reads." - "What if the proof of concept had failed?" "We'd have stopped at that gate. The point of gates is that failing one is a cheap, early answer."

Honesty note. Say this carefully: 189s to 12s is a proof-of-concept harness on 250 million rows (12.3s, rounded). It is not a claim that every query is now sub-second. This was a team decision. I wrote the proposal and ran the proof, and reviewers and leadership made the commitment.

Story 4. When the LLM lost to simple math

Answers: a data-driven decision · results that did not meet expectations · insisting on high standards · resisting the urge to ship something that looks good · ethics in AI. Project: Impact Analytics, Keep/Drop merchandise decision engine. Tags: 300-case harness, 80% CI gate, 73% lower cost at 100% coverage, and 74% deterministic baseline are on the resume. The ~63% blended score and the model names are verbal depth.

Words you need. - Article-season. One product (article) in one selling season. The engine scores 348k of them. - Deterministic score. A score computed by fixed math from sell-through and rate of sale. Same input, same answer, every time. - LLM lenses. Seven different angles the LLM is asked to judge from, combined by a "decider" step into one agent score. - Blend. Final score = 0.4 x deterministic score + 0.6 x agent score. Keep the article if the final score is 0.55 or higher. - Gold benchmark. A fixed set of cases with known correct answers, here 200 cases ("gold-200"). - CI promotion gate. An automatic check in the build pipeline. If accuracy on the evaluation set is below the bar, the change cannot be promoted.

Situation. The Keep/Drop engine blends deterministic KPI math with LLM judgement. On our 200-case gold benchmark, the deterministic baseline alone (at the production threshold of 0.65) scored 74%. The blended score with the LLM came in at about 63%. In other words, adding the LLM made accuracy on that benchmark worse, not better.

Task. Decide what to promote, protect quality for every future change, and pick a model that made sense on cost, without fooling ourselves with a number we had tuned to look good.

Action. 1. I did not retune the blend weights to chase the benchmark. Retuning weights on the same 200 cases until the number goes up is just fitting to the test. I froze the blend weights. 2. I built a 300-case proxy evaluation harness and wired an 80% accuracy gate into CI (gold_min_accuracy of 0.8 in eval.json). No prompt or model change gets promoted if it scores below that bar. 3. I compared models on the gold-200 benchmark for cost and completion. The cheaper model gave 73% lower live execution cost with 100% coverage, meaning all 200 cases completed with no failures or timeouts. 4. I kept the deterministic score as the safety net. If an LLM call times out, that item falls back to its deterministic baseline score. 5. Every output row is stamped with a config_hash, a SHA-256 fingerprint of the guardrails, parameters, prompts and catalog, so any decision can be traced to the exact configuration that produced it.

Result. We did not promote a change that the data said was worse. Live execution cost went down 73% at full coverage. Every future change has to clear the 80% gate. And the team has an honest baseline to beat instead of a flattering number.

What I learned. A good deterministic baseline is a feature, not an embarrassment. An LLM has to beat simple math before it earns more weight.

Likely follow-ups. - "Your gate is 80% but your baseline is 74%. Doesn't that mean you're failing?" "They're on different sets. 80% is the promotion gate on the 300-case proxy harness. 74% is the deterministic baseline on the separate gold-200 benchmark. I keep them apart on purpose." - "So what does the LLM add?" "The lens reasoning and the explanation step that planners can read, on top of a deterministic score that stays in the blend and acts as the fallback. The weights stay frozen until the evidence says otherwise." - "Why not retune?" "Because 200 cases is small. Tuning on them would raise the benchmark number without telling us anything about real tenants." - "Which models?" "If asked: we compared gpt-5.6-luna against gpt-5.4-mini. The names aren't on my resume because they change every few months. The method is the point."

Honesty note. Say this carefully: 80% is a CI promotion gate, not live accuracy for every tenant. 73% and 74% come from the gold-200 benchmark, not the 300-case file. Do not fuse them into one sentence like "80% accurate and 73% cheaper". There was no human review queue in Keep/Drop. Offline evaluations replaced critic or evaluator agents there.

Story 5. Designing AI that fails safely

Answers: anticipating problems before they happen · security and data protection · customer trust · designing for failure · build versus buy (why not Airflow). Project: Impact Analytics, Keep/Drop orchestration and the Ask Iris copilot. Tags: all mechanisms are on the resume. There are no SLA or usage numbers for Ask Iris, and none should be invented.

This is a design story, not an incident story. Nothing blew up. Use it when they ask how you prevent problems, not when they ask about a failure.

Words you need. - Multi-tenant. One system serving many retailer customers, whose data must never mix. - Circuit breaker. A switch that stops calling a failing service after repeated failures, so you stop wasting time and money on it. Like a fuse in your house. - Checkpoint. A saved record of finished work, so a restarted run skips what is already done. - WebSocket. A connection that stays open so the server and the browser can talk both ways, which is what a chat needs. - LangGraph supervisor. A LangGraph pattern where one "supervisor" step decides which sub-agent or tool runs next. - JWT (JSON Web Token). A signed token proving who the user is.

Situation. Planners use AssortSmart's AI output to make real buying decisions for retailers. The underlying ClickHouse fact table has 2.11 billion rows across many tenants. LLM providers time out and fail. A batch pass covers 88,000 items. And Ask Iris is a chat copilot that planners use to query KPIs and inspect AI decisions. The risks were clear: an LLM writing its own SQL against a 2.11-billion-row table, a run dying halfway and redoing expensive work, a chat session seeing another tenant's data, and an agent looping forever.

Task. Make the AI safe to run on real tenants before anything went wrong.

Action. 1. The LLM never queries the database. I decoupled inference from the master table. The system prepares the context for each item and hands it to the LLM as a JSON payload. The LLM never gets a SQL tool. Results are written back eventually consistent via ReplacingMergeTree. 2. Failure is planned for. I built a shared orchestration registry with hard timeouts, circuit breakers that trip after about five consecutive failures or a high failure fraction, and a graceful fallback to the deterministic baseline score when the LLM times out. 3. Runs resume instead of restarting. Durable checkpoints (det.json, agent_progress.json, and a --resume flag) let a restarted run skip deterministic scoring and LLM work that already finished. 4. Everything is traceable. A frozen config_hash is stamped on every output row, and custom JSON telemetry records tokens, cost in dollars, step duration and batch fallbacks. 5. Ask Iris cannot leak across tenants or loop. It runs over a JWT-secured WebSocket. The user's hierarchy access (plan_scope) is frozen at the socket handshake, so nothing said later in the chat can widen it. A LangGraph supervisor routes the work, and an evaluator loop is capped at three attempts (MAX_ATTEMPTS = 3). LangSmith traces each conversation. 6. I chose not to add Airflow or Temporal. We needed resume logic tied directly to ClickHouse inserts and config hashing, and a separate workflow platform was extra infrastructure we could not justify for that.

flowchart LR CH["ClickHouse master, 2.11B rows"] --> PREP["Context builder"] PREP -->|JSON payload only| LLM["LLM lenses"] LLM -->|timeout| FB["Deterministic fallback score"] LLM --> OUT["Scored rows stamped with config_hash"] FB --> OUT

What to notice: there is no arrow from the LLM back to the database. That missing arrow is the whole design.

Result. Keep/Drop runs finish even when the model provider fails, and a restart does not redo finished work. Ask Iris shipped as a planner copilot with tenant scope fixed at connection time. I keep the result qualitative because there are no SLA or usage numbers to quote.

What I learned. With LLMs, put a deterministic contract around the probabilistic part. Decide what the model is not allowed to do before you decide what it does.

Likely follow-ups. - "Why not let the LLM write SQL? It's more flexible." "Flexibility is the risk. A bad query on 2.11 billion rows costs money, can return wrong numbers, and in a multi-tenant system could cross a tenant boundary. Prepared JSON context is boring and safe." - "Why freeze scope at the handshake?" "Because the chat is untrusted input. If scope could change mid-conversation, a cleverly worded message could widen it. Fixing it when the socket opens means the check happens once, from the token." - "Why three attempts?" "It stops infinite loops and caps cost. After three tries the copilot returns its best answer instead of spinning." - "Is there an LLM orchestrator in Keep/Drop?" "No. The batch order is fixed: peer, decider, lenses, blend, explain. The supervisor pattern is in Ask Iris."

Honesty note. Say this carefully: LangSmith is on Ask Iris only, not on the Keep/Drop batch. There is no human review queue. Ask Iris is a shipped capability with no SLA or usage numbers. Do not attach Kafka, Flink or CDC to anything at Impact Analytics.

Story 6. The bug that pointed edits at the wrong line

Answers: dive deep · hardest bug you fixed · ownership of a migration · quality under deadline · migrating without breaking the live path. Project: Uber via EPAM, FRM Scoping Platform, reconciliation v1 to v2. Tags: MEASURED from the migration write-up and code (18 files, 1,268 lines added). The column-aliasing fix is part of the resume's SQLAlchemy 2.0 migration bullet.

Words you need. - Reconciliation (recon). Checking that the numbers in Oracle HFM (Hyperion Financial Management, Uber's consolidation system) match the numbers in the filed 10-Q quarterly report, line by line. - FSLI (Financial Statement Line Item). One line on the balance sheet or income statement, like Cash or Revenue. FRM uses a 4-level hierarchy, L1 to L4. - ORM (object-relational mapper). A library that maps database rows to code objects. SQLAlchemy is the Python one. - Column aliasing. Giving a selected column an explicit name in the query, such as AS fsli_id, so two columns with the same name do not collide. - Parallel run. Running the old and new versions side by side and comparing outputs before switching users over.

Situation. The v1 reconciliation endpoints were backed by Google Sheets. Recon lines had no stable ID in the database, so you could not attach a comment to a line or track it by quarter. The legacy read path also had a hidden identity problem. It turned raw SQL results into Python dictionaries with dict(zip(result.keys(), row)). The query joined the fact table (balance sheet or income statement) to the level_mapping table, and both tables had columns named uuid, level_id, fiscal_quarter and fiscal_year. The symptom: an edit to one recon line appeared to affect a different line.

Task. I owned migrating reconciliation from Sheets-backed v1 to MySQL-backed v2, under the quarterly close deadline, without breaking v1. And I had to kill the identity bug for good.

Action. 1. Found the root cause. When a join returns two columns both named uuid, zip pairs them by position and a Python dictionary keeps only the last one. So each row silently carried the level_mapping uuid instead of the fact row's uuid. The values on screen looked right. The identity was wrong, so PATCH-by-uuid and comment mapping hit the wrong line. 2. Fixed it structurally. I moved the reads to SQLAlchemy 2.0 select() on aliased() models and gave every projected column an explicit .label(), for example fsli_id for the fact identity and level_mapping_uuid for the mapping identity. Names can no longer collide. 3. Built v2 alongside v1. New endpoints GET /v2/recon_balance_sheet and GET /v2/recon_income_statement, with ORM models, Pydantic response schemas, repository readers and a service that builds the L1 to L3 tree and sums children into parents. v1 stayed untouched. 4. Ran them in parallel. QA compared v1 and v2 for the same period side by side. The test plan covered happy paths, an empty period, missing parameters returning 422, a check that the old v1 response shape was unchanged, and the invariant that every parent equals the sum of its children. 5. Cut over safely. The UI moved to v2 after staging verification, and v1 stayed as a fallback.

i = aliased(fact_model, name="i")
lm = aliased(LevelMapping, name="lm")
select(
    func.min(i.uuid).label("fsli_id"),              # the fact row's identity
    func.max(lm.uuid).label("level_mapping_uuid"),  # the mapping's identity, separately named
    lm.level1.label("level_1"),
)

What to notice: every column has its own label, so the dictionary built from the result can never overwrite one uuid with another.

Result. Reconciliation now lives in MySQL with stable line IDs keyed by quarter and year, so comments map to the right line and the HFM-versus-10-Q differences are queryable. The change was 18 files and 1,268 added lines. The wrong-identity class of bug cannot recur in the migrated reads.

What I learned. Mapping query results by position is a silent-corruption risk. Label everything, and run old and new side by side before you trust the new one.

Likely follow-ups. - "Why didn't anyone notice earlier?" "Because the numbers on screen were right. Only the hidden identity was wrong, and that only shows up when you write back, like an edit or a comment." - "Why is a wrong ID so bad here?" "This tool feeds audit evidence. A comment or a scope decision on the wrong financial line is a silent wrong answer, which is the worst kind." - "What else could silently go wrong?" "A duplicated leaf double-counts its parent, which is why we check parent equals sum of children. How to tell a story in 2 minutes

Two minutes is about 300 spoken words. Most people spend 90 seconds on the situation and run out of time before the part that matters. Flip it: most of your time goes on what you did.

flowchart LR S["Situation, 15 seconds"] --> T["Task, 10 seconds"] T --> A["Action, 60 to 70 seconds"] A --> R["Result, 15 to 20 seconds"] R --> L["Lesson, 10 seconds"]

What to notice: Action is more than half the time. Situation and Task together are under 30 seconds.

Step by step

  1. Open with a headline (5 seconds). One sentence that answers the question. "Yes. At Impact Analytics a weekly build needed 170 GB of memory and I made it fit without new hardware."
  2. Situation (15 seconds). Where, what system, why it mattered. Skip company history.
  3. Task (10 seconds). What you had to achieve, and the constraint that made it hard.
  4. Action (60 to 70 seconds). Three or four concrete steps, in order, in "I" language. Name one technical detail per step so it sounds real. This is where the interviewer decides your level.
  5. Result (15 to 20 seconds). The number, with how solid it is ("measured on a 250-million-row harness", "estimated"). If there is no number, say the honest qualitative outcome.
  6. Lesson (10 seconds). One sentence you would act on next time.
  7. Stop. Do not add "and also". Let them ask follow-ups. Stopping cleanly sounds senior.

Rules that make stories land

  • "I", not "we", for your part. Credit others by role: "the data pipeline team", "my two mentees", "the reviewers".
  • One story, one project. Never mix Masters Kafka with Uber Menu Kafka, or "led 3" with "mentored 2".
  • Failures end in process. Every failure story should end with a change that stops the class of problem (Stories 8, 9, 15).
  • Conflict stories have no villain. Frame it as competent people disagreeing about an assumption (Stories 3, 7).
  • Say the honesty caveat before they find it. "This was caught in CI, not production." "That rate was measured while the copy was in flight." Volunteering it builds trust.
  • Take five seconds if you need them. "Let me pick the best example" is fine.
  • If you have not lived it, say so. "I haven't had that exact situation. The closest is..." Never invent.

Before each loop

  • Pick 2 to 3 stories for that company from the map above.
  • Check you can say each one's result number and tag without looking.
  • Check that no two stories you plan to tell come from the same incident.

Handling follow-ups

Interviewers dig into one or two actions to see if you really did them. For each story, be ready to go one level deeper on any action: the exact setting, the alternative you rejected, and what you would do differently. The "Likely follow-ups" under each story are the ones to rehearse. If you do not remember a detail, say "I don't remember the exact figure, but the order of magnitude was..." only when you actually know the order of magnitude. Otherwise say you'd need to check.
