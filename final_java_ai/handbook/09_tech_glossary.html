Tech Glossary: every technology on my resume, explained

How to use this page

  • It covers every technology on the Java + Python resume (Tarun_Mittal_SSE_5yr_Java_AI.pdf, Final Java + AI): the Skills line plus each project's Tech line.
  • Read it the week before interviews, and again the night before a round that names a specific tool in the job description.
  • Memorise three things per entry: the one-line definition, where I used it (or that it is skills-level), and one "why this and not the alternative" sentence.
  • The project stories live in the chapters. This page explains the tools. Jump to IA core platform, IA agentic AI, Uber FRM, Uber Menu and ANZ, Masters India, GeeksforGeeks and numbers explained for the full stories.

How to read the labels

Every entry has a depth label. It tells you how strongly you may claim the technology.

  • Production means the technology appears in a resume bullet or a project Tech line, and I did real work with it in a shipped system. You can go deep.
  • Project means it is on a project Tech line and I used it there, but no bullet is about it. Speak about it confidently but keep claims qualitative. Do not invent numbers.
  • Skills-level means it is on the Skills line as literacy. I can explain how it works and when I would pick it. I do not claim production ownership. If asked "did you run this in production?", the honest answer is "No, here is what I know and where I would use it."

Numbers also carry tags in the project chapters. MEASURED means there is a log, doc or code behind it. ESTIMATED means arithmetic I can show. HISTORICAL means it comes from my past work records. TARGET means a design goal ("targeting"). On this page I only repeat numbers that are already on the resume or in the locked facts.

Code snippets on this page are teaching sketches. They show how the technology works in general. They are not copies of company code. When you speak, describe what we built in words, and use the snippet only to show you understand the mechanism.

1. Languages

Java

Depth: Production. Uber FRM (via EPAM) and Masters India.

What it is. Java is a statically typed, object-oriented language. You compile it to bytecode, and the JVM (Java Virtual Machine) runs that bytecode on any machine. It is the default language for large business backends because the ecosystem (Spring, Hibernate, Kafka clients, monitoring agents) is mature and well tested. Think of a heavy-duty commercial kitchen: it takes a moment to fire up, but once running it serves a huge crowd reliably all day.

How it works (what interviewers probe). - The JVM and JIT. The JVM first interprets bytecode, then the JIT (Just-In-Time) compiler turns hot methods into fast machine code while the app runs. That is why a Java service gets faster after warm-up. - Heap and garbage collection (GC). Objects live on the heap. The garbage collector frees objects nobody references. Most collectors are generational: new objects start in the young generation, most die young and are cleaned cheaply, and survivors move to the old generation. G1 is the default collector in modern Java. ZGC and Shenandoah aim for very short pauses on big heaps. - Threads. A classic Java thread maps to one operating-system thread, which costs memory and context switches. Servlet-based Spring services use one thread per request, so a pool of threads bounds how many requests run at once. - Virtual threads (Java 21). Very light threads managed by the JVM. Blocking code (a JDBC call, an HTTP call) parks the virtual thread instead of holding an OS thread, so you can have many thousands. Same blocking style, much cheaper waiting. - Concurrency tools. ExecutorService pools, CompletableFuture for async composition, and java.util.concurrent locks and atomics. Bounded pools are how you protect a slow downstream system.

// Illustrative sizes. A bounded pool caps calls to a slow external portal.
ExecutorService irpPool = new ThreadPoolExecutor(
        16, 16, 0L, TimeUnit.MILLISECONDS,
        new ArrayBlockingQueue<>(1_000),               // bounded queue, no unbounded growth
        new ThreadPoolExecutor.CallerRunsPolicy());    // back-pressure when full

Future<IrpResponse> f = irpPool.submit(() -> irpClient.register(invoice));
IrpResponse resp = f.get(10, TimeUnit.SECONDS);        // hard timeout per call

// Java 21 virtual threads: one cheap thread per task, same blocking code.
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    exec.submit(() -> irpClient.register(invoice));
}

Where I used it. - Uber FRM (via EPAM): the scoping backend. 36 Spring Boot endpoints on Spring Data JPA, Hibernate and MySQL, tested with JUnit and built with Bazel. - Masters India: the Spring Boot microservices that replaced the PHP monolith, including the Kafka consumers of the bulk e-invoicing pipeline on PostgreSQL.

Why it was chosen there. On FRM, Spring Boot services were the team's standard, and finance logic benefits from strong typing and a mature ORM. At Masters, a long-lived migration off PHP needed a stable, typed platform with first-class Kafka, PostgreSQL, Redis and New Relic support.

Alternatives and when I'd pick them. Go for a high-traffic edge or a raw-throughput tool, which is why the IA HTTP platform and the ClickHouse data pump are in Go. Python when the work is AI orchestration, because the model and agent libraries are Python-first. Kotlin if a JVM team wants less boilerplate.

Likely interview questions. - "How does garbage collection work in Java?" Objects are allocated on the heap, and the collector frees anything no longer reachable from live references. Modern collectors are generational because most objects die young, so cleaning the young generation is cheap and frequent. G1 is the default and balances throughput with pause targets. If pauses hurt on a large heap I would look at ZGC. I tune from GC logs, not by guessing. - "Platform threads or virtual threads?" Platform threads are OS threads, so you keep them in bounded pools. Virtual threads are cheap JVM-managed threads that park while blocked, which suits services that mostly wait on databases and HTTP calls. They do not make CPU-heavy work faster, and you still need limits on the downstream system, such as the connection pool size. I know them well conceptually and do not claim them on my past projects. - "Why Java for FRM and Masters, but Go and Python at Impact Analytics?" Each service uses what fits its job. FRM and Masters are transactional business services with heavy ORM and messaging work, which is Spring's home ground. The IA edge is plumbing at 10k peak RPS, so Go. The IA agent plane needs LangGraph and model SDKs, so Python. - "How do you find a memory leak in a Java service?" Watch heap usage after full GCs. If the floor keeps rising, take a heap dump and look at what holds the most retained memory. The usual suspects are unbounded caches, static collections, ThreadLocal values in pooled threads and unclosed resources.

Numbers tied to it. None on its own. The Java projects carry the numbers: from 14 days to 3 days reconciliation on FRM, and from 1.2 seconds to 300 milliseconds p95 at Masters.

Python

Depth: Production. Impact Analytics agent plane, Uber Menu and GeeksforGeeks.

What it is. Python is a general-purpose programming language known for readable code and a huge library ecosystem. It is the default language for AI work because almost every model provider and AI framework ships a Python library first. Think of it as a well-stocked kitchen: not the fastest stove, but every ingredient and tool is already on the shelf.

How it works (what interviewers probe). - The GIL (Global Interpreter Lock). Only one thread runs Python bytecode at a time inside one process. That hurts CPU-heavy work but barely matters for I/O-heavy work like calling APIs or databases, because threads release the lock while they wait. For CPU-heavy work you use multiple processes. - asyncio lets one thread juggle thousands of waiting network calls (see asyncio). - Type hints do nothing at runtime by themselves, but tools like Pydantic and FastAPI read them to validate data. - Packaging and environments (virtualenv, pip, lock files) keep dependencies reproducible.

# I/O-bound work: threads or asyncio are fine despite the GIL.
# CPU-bound work: use processes.
from concurrent.futures import ProcessPoolExecutor

def score(article):            # pure CPU math
    return article["sell_through"] * 0.5 + article["rate_of_sale"] * 0.5

with ProcessPoolExecutor() as pool:
    scores = list(pool.map(score, articles))

Where I used it. - Impact Analytics (AssortSmart): the agent plane. Keep/Drop, Missed Opportunities and Top Style batch scoring, and the Ask Iris copilot (FastAPI plus LangGraph). - Uber Eats Menu (via EPAM): the Selenium fleet and the LangChain RAG extraction pipeline. - GeeksforGeeks: the Django backend.

Why it was chosen there. On the AI side, the LLM and agent libraries are Python-first, so fighting that would cost time. Menu extraction lives on LangChain, Gemini and Selenium, which are all strongest in Python. GeeksforGeeks was already a Python shop, and Django was the fastest way off PHP.

Alternatives and when I'd pick them. I pick Go when the job is a high-traffic edge or a raw-throughput tool, which is exactly why the IA HTTP platform and the ClickHouse data pump are in Go. I pick Java and Spring Boot for transactional business services with heavy ORM and messaging work, which is what FRM and Masters were.

Likely interview questions. - "Does the GIL make Python bad for backends?" Not for most backends. Most backend time is spent waiting on databases and other services, and threads or asyncio release the GIL while waiting. When I have truly CPU-heavy work I move it to processes or to a compiled language. At Impact Analytics we did both: Python for the agent plane, Go for the high-RPS edge. - "When would you move a Python path to Go?" When the path is hot, latency-sensitive and mostly plumbing, not AI logic. Our 10k peak RPS edge is Go. The LLM orchestration stays in Python because that is where the libraries are.

Numbers tied to it. None on its own. The Python projects carry the numbers (for example from 24 hours to 2 hours onboarding on Menu, 348k article-seasons scored at Impact Analytics, 10K+ daily queries at GeeksforGeeks).

Go

Depth: Production. Impact Analytics.

What it is. Go (also called Golang) is a compiled, statically typed language from Google. It produces a single binary, starts fast, and makes running thousands of tasks at once cheap. Think of it as a lean delivery van: small, quick to start, and able to carry many parcels at the same time.

How it works. - Goroutines are very light threads managed by the Go runtime. You can start tens of thousands of them. - Channels pass data safely between goroutines, so you share memory by communicating. - context.Context carries deadlines and cancellation through every call. This is how "nested timeouts" work: a request deadline is passed down, and each database call gets an even shorter one. - Static binary and garbage collector. Easy to ship in a small container, with predictable latency for most web workloads. - Interfaces are implicit. A type satisfies an interface just by having the methods, which keeps code testable.

// Double buffering: read the next batch while the previous one is being sent.
batches := make(chan [][]any, 1)   // buffer of one = one batch in flight

go func() {                        // reader goroutine
    for b := readNext(500_000); b != nil; b = readNext(500_000) {
        batches <- b               // blocks only if the sender is still busy
    }
    close(batches)
}()

for b := range batches {           // sender loop
    send(ctx, b)                   // INSERT into target cluster
}

Where I used it. All at Impact Analytics: - C1: the multi-tenant Go/Gin platform at 10k peak RPS, with Google Wire, native h2c, nested timeouts and Datadog tracing. - C2: the KPI formula tokenizer and parser that turns operator-written formulas into parameterized ClickHouse SQL. - C5: the custom Go native-TLS data pump that copied ClickHouse rollups between Cloud clusters at about 344k rows per second, in 500k-row double-buffered batches.

Why it was chosen there. The platform edge needs predictable latency under load and cheap concurrency. The data pump needs tight control over memory and buffers. Both are Go's sweet spot.

Alternatives and when I'd pick them. Python FastAPI when the work is AI orchestration (that is our agent plane). Java and Spring Boot for ORM-heavy transactional business services, as on FRM and Masters. Rust only if I needed zero garbage-collection pauses, which we did not.

Likely interview questions. - "Why Go for the edge and Python for the agents?" Each language does what it is best at. The edge is plumbing at 10k peak RPS, so I want goroutines and predictable latency. The agent plane needs LangGraph and the model SDKs, which are Python-first. Business rules and authorization stay in one place so the two do not diverge. - "How did you get about 344k rows per second in Go?" Two season streams ran in parallel, each about 150k to 190k rows per second. Each used 500k-row columnar batches and double buffering, so reading the next batch overlapped with sending the previous one. It is ingest rate, not requests per second. - "How do you avoid goroutine leaks?" Every goroutine gets a context it listens to, and every channel has a clear owner who closes it. I also bound concurrency with worker pools instead of starting one goroutine per item.

Numbers tied to it. 10k peak RPS (C1). About 344k rows per second combined, 500k-row batches, partitions up to 4.09B rows (C5). Say "344 thousand rows per second", never "344k RPS".

SQL

Depth: Production. Every project.

What it is. SQL (Structured Query Language) is the language you use to ask databases questions and change data. You describe what you want, and the database figures out how to get it. Think of it as ordering at a restaurant: you name the dish, the kitchen decides the steps.

How it works. - Joins combine tables on a key. Duplicate column names across joined tables are a classic trap. - Indexes let the database jump to rows instead of scanning everything. EXPLAIN shows whether an index is used. - Transactions group several changes so they all happen or none happen (atomicity). - GROUP BY and aggregations summarise data. In analytical databases, aggregations are where memory blows up. - Parameterized queries keep user input separate from SQL text, which blocks SQL injection.

-- The FRM column-aliasing trap, and the fix.
-- Bad: both tables have "uuid", the driver may map the wrong one.
SELECT * FROM balance_sheet bs JOIN level_mapping lm ON bs.level_id = lm.uuid;

-- Good: explicit, labelled columns.
SELECT bs.uuid AS line_uuid, lm.uuid AS level_uuid, bs.amount
FROM balance_sheet bs JOIN level_mapping lm ON bs.level_id = lm.uuid;

Where I used it. - Uber FRM: MySQL schema, reporting SQL allowlists, and the column-aliasing bug fix (duplicate column names in joined raw SQL silently mapped rows to the wrong uuid). - Impact Analytics: ClickHouse SQL for six rollup tables, temporal-chunked INSERT SELECT, and the formula parser that emits parameterized SQL fragments. - Masters India: PostgreSQL query and index fixes that were part of the p95 latency win. - GeeksforGeeks: MySQL for users, votes and subscriptions.

Why it matters. Every one of my performance stories ends up in SQL: an index, a rollup, a smaller GROUP BY, or a labelled join.

Alternatives. None really. Even NoSQL and stream tools now offer SQL-like layers. The real choice is which engine runs your SQL.

Likely interview questions. - "Tell me about a SQL bug you fixed." On FRM, joined raw SQL had duplicate column names, so rows were silently mapped to the wrong uuid. Nothing crashed, the numbers were just wrong. We fixed it with aliased selects and explicit labels, and the Spring Data JPA / Hibernate migration removed that class of bug, because results map to typed entities and DTO projections by name. - "How do you find a slow query?" I run EXPLAIN, check whether the expected index is used, and check how many rows are read versus returned. If an analytical query must scan huge data on every request, I pre-aggregate instead, which is what the ClickHouse rollups do.

Numbers tied to it. 19M raw GL rows migrated off Sheets (FRM). From 189 seconds to 12 seconds on a 250M-row harness (IA).

C and C++

Depth: Skills-level. Literacy, no production ownership claim.

What it is. C is a low-level language that gives you direct control over memory. C++ adds classes, templates and a large standard library on top. They are what operating systems, databases and game engines are written in. ClickHouse, for example, is written in C++. Think of them as driving a manual car: more control, and more ways to stall.

How it works. - Manual memory. In C you malloc and free yourself. Forgetting free leaks memory. Freeing twice crashes. - Pointers hold memory addresses. Bugs here cause crashes and security holes. - RAII in C++. Objects clean up their resources in their destructor, and smart pointers (std::unique_ptr) automate freeing. - Undefined behaviour. Some mistakes, like reading past an array, have no defined result. The program may seem fine and then fail later.

#include <memory>
#include <vector>
std::unique_ptr<std::vector<int>> v = std::make_unique<std::vector<int>>(1000);
// No delete needed. Memory is freed when v goes out of scope (RAII).

Where I used it. Skills-level only. I list them for systems literacy and data-structures work. I do not claim production C or C++ services.

Why it is on the resume. It signals I understand what Java, Go and Python hide from me: stack versus heap, memory layout, and why garbage collection costs something.

Alternatives. For new systems work I would pick Go (simpler, garbage collected) or Rust (memory safety without garbage collection).

Likely interview questions. - "Have you written production C++?" No. I list C and C++ as systems literacy. My production work is Java, Python and Go. I understand manual memory, pointers and RAII, which helps me reason about things like ClickHouse memory limits. - "Go garbage collection versus C++ manual memory?" Go trades a small, mostly predictable pause cost for safety and speed of development. C++ gives full control, but every allocation is your responsibility.

Numbers tied to it. None.

Spring Boot

Depth: Production. Uber FRM F1 and Masters India MI1.

What it is. Spring Boot is a Java framework for building production-ready services quickly. It sits on top of the Spring Framework and makes sensible choices for you: an embedded web server, JSON handling, database connection pooling, health checks and configuration. You add a "starter" dependency and it wires the pieces together. Think of a fully fitted restaurant you can lease: kitchen, tables and fire safety are already installed, and you only bring the menu.

How it works (what interviewers probe). - IoC (Inversion of Control) container and dependency injection. Spring creates your objects ("beans") and hands each one the beans it needs, usually through the constructor. You mark classes with @Service, @Repository or @RestController, or declare them with @Bean. - Auto-configuration and starters. spring-boot-starter-web pulls in Spring MVC, an embedded Tomcat server and Jackson for JSON. Auto-configuration classes switch on only when the right library is on the classpath, and any bean you define yourself wins over the default. - Embedded server, fat jar. The service ships as one jar and starts with java -jar app.jar, which fits Docker images well. - Externalized config and profiles. application.yml, environment variables and @ConfigurationProperties keep settings out of code. Profiles switch config per environment. - Actuator. Built-in health, readiness and metrics endpoints for load balancers and monitoring. - The classic trap. @Transactional and @Async work through proxies. A call from one method to another inside the same class skips the proxy, so the annotation silently does nothing.

@RestController
@RequestMapping("/v1/scoping/lines")
public class ScopingLineController {

    private final ScopingService service;               // controller -> service -> repository

    public ScopingLineController(ScopingService service) {
        this.service = service;                          // constructor injection
    }

    @GetMapping("/{lineId}")
    public ScopingLineDto get(@PathVariable String lineId) {
        return service.get(lineId);
    }

    @PatchMapping("/{lineId}/status")
    public ScopingLineDto updateStatus(@PathVariable String lineId,
                                       @Valid @RequestBody StatusUpdate body) {
        return service.updateStatus(lineId, body);       // version checked inside, see Hibernate
    }
}

public record StatusUpdate(@NotNull ReviewStatus status,  // Draft, Review, ReOpen, Closed
                           @NotNull Long version) {}      // for optimistic locking

Where I used it. - Uber FRM F1: 36 Spring Boot endpoints automating custom financial math and the nested 4-level FSLI (Financial Statement Line Item) hierarchy, L1 to L4, with dynamic quarter-annualization. The service is layered as controller, service and repository on Spring Data JPA, Hibernate and MySQL on Uber's SOADB. If asked for the split: about 31 functional routes in the scoping service plus the collaboration-service APIs (comments and notifications) from the technical design doc make 36. - Masters India MI1: I led the migration of a legacy PHP monolith to Spring Boot microservices using the strangler pattern with a canary per route, and mentored 2 engineers through it. p95 latency went from 1.2 seconds to 300 milliseconds across 1,500+ enterprise clients, and throughput went from 700 to 4,000 requests per minute.

Why it was chosen there. Finance (FRM) and tax (Masters) data both need typed contracts, real transactions and a mature ORM, which is exactly what the Spring stack gives. At Masters it also had first-class clients for Kafka, PostgreSQL and Redis, and a New Relic Java agent, so the new services were observable from day one.

Alternatives and when I'd pick them. Quarkus or Micronaut when startup time and memory matter a lot, for example in serverless functions. Go Gin for a high-RPS edge, which is what the IA platform uses. FastAPI for AI orchestration, which is the IA agent plane. Django when I want an admin panel and the full product toolkit, which is what GeeksforGeeks used.

Likely interview questions. - "How did Spring Boot help bring p95 from 1.2 seconds to 300 milliseconds?" The framework alone did not do it. The biggest win was taking slow government IRP (Invoice Registration Portal) calls off the request thread, using a non-blocking WebClient and Kafka-backed async jobs. Connection pooling with HikariCP, query and index fixes, and Redis for hot reads did the rest. Spring Boot made each of those a configuration choice instead of custom plumbing. - "How do you migrate a PHP monolith without a big bang?" With the strangler pattern. A routing layer sits in front of both systems. We moved one route at a time to Spring Boot, sent a small canary share of traffic to the new route, compared results and errors, then switched fully and retired the PHP route. Rollback was just a routing change. - "How does auto-configuration work?" Spring Boot ships configuration classes guarded by conditions such as "this class is on the classpath" and "no bean of this type exists yet". Adding the Postgres driver and the JPA starter is enough to get a DataSource, a connection pool and an EntityManager. Spring MVC

Depth: On the Skills line. It is the web layer inside the Spring Boot services on FRM and Masters. No bullet is about it on its own.

What it is. Spring MVC is Spring's web framework. It turns HTTP requests into calls on your controller methods and turns the return values back into HTTP responses, usually JSON. Spring Boot uses it whenever you add the web starter. Think of a hotel front desk: every guest walks up to the same desk, and the desk sends each one to the right room.

How it works. - Front controller. One DispatcherServlet receives every request. A handler mapping finds the controller method for the URL and HTTP verb. - Argument binding. @PathVariable, @RequestParam and @RequestBody fill method parameters. Jackson converts JSON to Java objects and back. - Bean Validation. Put @Valid on the request body and constraints like @NotNull, @Size or @Pattern on the DTO (Data Transfer Object) fields. Bad input becomes a 400 response before your code runs. - Central error handling. A @RestControllerAdvice class maps exceptions to status codes in one place. - Thread per request. On the default servlet stack, each request holds one server thread from Tomcat's pool until it finishes. Blocking calls are fine, but they hold that thread while they wait.

@RestControllerAdvice
public class ApiErrors {

    // A stale @Version on update becomes a clean 409 instead of a 500.
    @ExceptionHandler(ObjectOptimisticLockingFailureException.class)
    public ProblemDetail conflict(ObjectOptimisticLockingFailureException e) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT,
                "Someone else changed this line. Reload and try again.");
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ProblemDetail invalid(MethodArgumentNotValidException e) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "Invalid request body");
    }
}

Where I used it. Inside every Spring Boot service I built. The 36 FRM endpoints and the Masters routes are Spring MVC controllers, with Bean Validation on request DTOs and central error mapping. I present it as part of the Spring Boot work, not as a separate achievement.

Why it was chosen there. The blocking, thread-per-request model is simple to reason about and matches JDBC and Hibernate, which are blocking too.

Alternatives and when I'd pick them. Spring WebFlux, the reactive and non-blocking stack, when a service holds a very large number of slow concurrent connections and its whole call chain is non-blocking. With JDBC and JPA underneath, WebFlux gains little. Java 21 virtual threads give much of the same benefit while keeping plain MVC code.

Likely interview questions. - "Walk me through a request in Spring MVC." Tomcat accepts the connection and hands it to the DispatcherServlet. Filters run first, for example security. The handler mapping picks the controller method, arguments are bound and validated, the method runs, and Jackson writes the return value as JSON. Any exception goes to the @RestControllerAdvice, which turns it into the right status code. - "Spring MVC or WebFlux?" MVC by default, because it is simpler to write, debug and trace. At the edge, on the DTO with Bean Validation, so bad data never reaches the service layer. Spring Data JPA

What it is. JPA (Jakarta Persistence API, formerly Java Persistence API) is the standard Java specification for ORM (Object Relational Mapping), which lets you work with database rows as Java objects. Spring Data JPA sits on top of it. You declare a repository interface, and Spring writes the implementation for you. Think of ordering from a menu by name: you say findByQuarterAndStatus, and the kitchen knows how to cook it.

How it works. - Repositories. JpaRepository<Entity, Id> gives you save, findById, paging and sorting for free. - Derived queries. A service method runs in one transaction, so several repository calls commit together or roll back together. By default only unchecked exceptions trigger a rollback.

Hibernate

Depth: Production. Uber FRM (under Spring Data JPA) and the Masters India Tech line.

What it is. Hibernate is the most widely used implementation of JPA. It maps entity classes to tables, generates the SQL, and tracks every object you load so it knows what changed. Spring Data JPA is the friendly layer on top, and Hibernate does the actual work underneath. Think of a personal assistant who remembers every file you took out today, notices which ones you scribbled on, and refiles exactly those when you leave.

How it works (the four ideas interviewers always ask about). - Persistence context. Inside one transaction, Hibernate keeps one Java object per database row it has loaded. This is the first-level cache. Calling findById twice for the same id returns the same object and fires only one SQL query. - Dirty checking. When the transaction flushes, Hibernate compares each managed entity with the snapshot it took on load and writes an UPDATE only for what changed. You change a field and do not need to call save. - Lazy loading and the N+1 problem. Related entities can load lazily, on first access. Looping over 50 parents and touching each one's lazy collection fires 1 query for the parents plus 50 more, which is N+1. Fixes are JOIN FETCH, @EntityGraph, batch fetching, or a DTO projection. Touching a lazy field after the transaction closes throws LazyInitializationException. - @Version optimistic locking. A version column on the entity. Hibernate adds AND version = ? to every update and bumps the version. If zero rows match, someone else changed the row first, and Hibernate throws an optimistic lock exception, which the API turns into a 409.

@Entity
@Table(name = "scoping_assessments")
public class ScopingAssessment {
    @Id
    private String uuid;                         // deterministic SHA-256 natural key

    @Enumerated(EnumType.STRING)
    private ReviewStatus status;                 // Draft, Review, ReOpen, Closed

    @Version
    private long version;                        // optimistic row-locking

    @ManyToOne(fetch = FetchType.LAZY)
    private ScopingPage page;

    public void setStatus(ReviewStatus status) { this.status = status; }
}

// Inside a @Transactional service method. No save() call is needed.
ScopingAssessment a = repo.findById(uuid).orElseThrow();
a.setStatus(ReviewStatus.REVIEW);
// At commit, dirty checking runs:
// UPDATE scoping_assessments SET status = 'REVIEW', version = 8 WHERE uuid = ? AND version = 7

// N+1 fix: load pages and their assessments in one query.
@Query("select distinct p from ScopingPage p join fetch p.assessments where p.quarter = :q")
List<ScopingPage> pagesWithAssessments(@Param("q") String quarter);

Where I used it. - Uber FRM F2 and F3: Hibernate runs under the Spring Data JPA migration. @Version gives the optimistic row-locking that keeps multi-user review edits safe, @Transactional gives the atomic cross-table syncs, and explicit fetch plans keep queries predictable. - Masters India: Hibernate is on the Masters Tech line as the ORM for the Spring Boot microservices on PostgreSQL. Query and index fixes were part of the p95 latency win. If asked for specifics, keep them at that level and do not invent a particular N+1 story.

Why it was chosen there. Finance review work has rare conflicts that must never silently overwrite each other, which is exactly what @Version handles. Dirty checking keeps update code short and readable, so reviewers can focus on business rules.

Alternatives and when I'd pick them. EclipseLink, the other main JPA implementation. jOOQ or JdbcTemplate when I want SQL-first code with no hidden queries. Pessimistic locking (@Lock(PESSIMISTIC_WRITE), which issues SELECT ... FOR UPDATE) when many writers fight over the same row.

Likely interview questions. - "What is the N+1 problem and how do you fix it?" You load N parent rows with one query, then touching each parent's lazy relation fires one more query per parent. It looks fine in tests with three rows and falls over with three thousand. I catch it by turning on SQL logging or counting statements in tests, and fix it with JOIN FETCH, an entity graph, batch fetching, or a projection that selects exactly the columns the screen needs. - "How does @Version work, and what does the user see?" Every update includes the version the user read. If another reviewer saved first, the version no longer matches, zero rows update and Hibernate throws. Our API maps that to a 409 Conflict, and the UI asks the user to reload. Nobody's change is silently lost. - "Why did my entity update without calling save?" Because it was managed by the persistence context inside a transaction. Dirty checking found the changed field at flush and wrote it. That is a feature, but it also means accidental setter calls get persisted, so keep transactions short and intentional. - "First-level versus second-level cache?" The first-level cache is the persistence context, one per transaction, always on. The second-level cache is shared across transactions and optional. I would only add it for read-mostly reference data, because stale cache entries in finance data are worse than a database read.

HikariCP

Depth: Project. It is the connection pool behind the Masters latency story. It is not named on the Skills line.

What it is. HikariCP is a fast, lightweight JDBC connection pool and the default pool in Spring Boot. Opening a database connection costs a network round trip, authentication and server memory, so a pool keeps a small set of connections open and lends them to requests. Think of a taxi rank: cabs wait ready at the stand, instead of calling a new cab from across town for every trip.

How it works. - maximumPoolSize caps how many connections exist. Extra requests wait for a free one. - connectionTimeout is how long a request waits before failing fast. Failing fast is better than piling up threads. - maxLifetime retires connections before the database or a firewall drops them silently. - leakDetectionThreshold logs a warning when code holds a connection too long, which usually means a missing close or a slow call inside a transaction. - Sizing. Smaller than people expect. HikariCP's own guide starts from roughly cores times 2 plus disk spindles. Pool size times the number of service instances must stay under the database's connection limit.

    hikari:
      maximum-pool-size: 20
      minimum-idle: 5

      max-lifetime: 1800000             # 30 minutes, retire before the server drops it
      leak-detection-threshold: 20000   # warn if a connection is held over 20 s

Where I used it. Masters India MI1: connection pooling was one of the four contributors to the p95 drop from 1.2 seconds to 300 milliseconds, together with non-blocking IRP calls, query and index fixes, and Redis for hot reads. PostgreSQL uses one server process per connection, so a bounded, reused pool matters a lot there. Because HikariCP is the Spring Boot default, it is also what a JDBC DataSource uses in any Spring Boot service unless someone replaces it.

Why it was chosen there. Re-opening connections per request adds latency to every call and can exhaust the database under spikes. A pool turns that into a cheap borrow and return.

Alternatives and when I'd pick them. PgBouncer, a server-side pooler shared by many service instances, when there are so many instances that per-app pools would exceed the database's limit. The two are often used together. Older pools like c3p0 or Tomcat JDBC are rarely chosen today.

Likely interview questions. - "Why does pooling cut latency?" Each new connection means a TCP handshake, possibly TLS, authentication and a new server process on Postgres. Borrowing an open connection skips all of it. Under load it also stops the database from being flooded with new connections. - "How do you size a pool?" Start small, around cores times 2, then measure wait time on the pool and query latency. A bigger pool often makes things slower, because the database spends its time switching between too many active queries. Multiply by instance count and check it against the database limit. - "What happens when the pool is exhausted?" Requests wait up to the connection timeout and then fail fast with a clear error. The usual root cause is not the pool size but a slow query or an external call made while holding a connection. Leak detection and pool metrics (active, idle, pending) find it.

Numbers tied to it. Part of the Masters p95 drop from 1.2 seconds to 300 milliseconds. No pool-specific number is claimed.

Spring Batch

Depth: Skills-level. On the Skills line. It fits the Masters chunked bulk imports, but no resume bullet names it.

What it is. Spring Batch is a framework for batch jobs: read a large number of records, process them, and write them out in chunks, with every chunk's progress recorded so a failed job can restart where it stopped. Think of moving a library: you fill a box with books, seal it, load it, and tick the box number in a ledger. If the truck breaks down, you restart from the first unticked box instead of from the first book.

How it works. - Job and steps. A job is a sequence of steps. A chunk-oriented step has an ItemReader, an optional ItemProcessor and an ItemWriter. - Chunks and commits. Items are read and processed one by one, then written and committed together every N items in one transaction. - JobRepository. Execution state lives in database tables, so a restart skips committed chunks. - Skip and retry policies. Skip bad rows up to a limit, retry transient errors a bounded number of times. - Job parameters identify a run, so the same input file does not accidentally run twice as a new job. - Scaling with multi-threaded or partitioned steps.

@Bean
Step validateInvoices(JobRepository repo, PlatformTransactionManager tx,
                      ItemReader<InvoiceRow> reader,
                      ItemProcessor<InvoiceRow, ValidatedInvoice> validator,
                      ItemWriter<ValidatedInvoice> writer) {
    return new StepBuilder("validateInvoices", repo)
            .<InvoiceRow, ValidatedInvoice>chunk(500, tx)    // illustrative chunk size
            .reader(reader)                                  // rows from the uploaded file
            .processor(validator)                            // schema, GSTIN format, duplicates
            .writer(writer)                                  // idempotent, keyed write per batch
            .faultTolerant()
            .skip(InvalidRowException.class).skipLimit(100)
            .retry(TransientDataAccessException.class).retryLimit(3)
            .build();
}

Where I used it. Skills-level. The place it fits is the Masters India bulk e-invoicing imports (MI2). A large invoice file is split into batches, each batch gets the idempotency key client plus file hash plus batch index, and a restart only redoes unfinished batches. That is the chunk-and-restart model Spring Batch formalises. Spring Batch is on my Skills line, not on the Masters Tech line, so I explain it at the pattern level and do not quote Spring Batch-specific numbers.

When I'd pick it. Large, finite, restartable jobs: file imports, end-of-day reconciliations, data migrations and bulk exports.

Alternatives and when I'd pick them. Kafka consumers for continuous event streams, which is what carried stage events at Masters. Plain @Scheduled or @Async methods for small background tasks such as reminders or cleanup. Airflow or Temporal when a workflow spans several systems. Spark for very large data processing.

Likely interview questions. - "Chunk step or tasklet?" A chunk step is for "many items, read, process, write", with commits every N items. A tasklet is one unit of work, like "call this stored procedure" or "delete yesterday's temp files". - "How does restart work?" The JobRepository records the last committed chunk for each step. Restarting the same job instance resumes from there. The writer must still be idempotent, because the chunk that was in flight during the crash is replayed. - "Spring Batch or Kafka consumers?" Spring Batch for a finite job with a clear start and end, like one uploaded file. Kafka consumers for an endless stream of events that several services read. REST

Depth: Production. FRM, Masters, GFG, IA.

What it is. REST (Representational State Transfer) is a style for designing APIs over HTTP. Everything is a resource with a URL, and you act on it with standard verbs: GET reads, POST creates, PUT replaces, PATCH updates part, DELETE removes. Think of a library with labelled shelves: the shelf address tells you what, the verb tells you what to do.

How it works. - Resources and verbs. GET /invoices/123, POST /imports. - Status codes. 200 OK, 201 Created, 400 bad input, 401 not logged in, 403 not allowed, 404 not found, 409 conflict, 429 too many requests, 5xx server error. - Idempotency. GET, PUT and DELETE should be safe to repeat. POST is not, unless you add an idempotency key. - Versioning and pagination. /v1/... paths, and cursor-based pages for big lists. - Statelessness. Each request carries its own auth (for example a JWT), so any server can handle it.

PATCH /v1/scoping/lines/abc123/status
Content-Type: application/json

{"status": "Review", "version": 7}

A 409 Conflict comes back if someone else already moved the line to version 8. That is optimistic locking expressed in REST. In Spring Boot the @Version check fails in Hibernate and a @RestControllerAdvice maps it to 409 (see Spring MVC).

Where I used it. FRM's 36 Spring Boot endpoints, the Masters India Spring Boot microservices, the GeeksforGeeks voting, pinning and locking APIs in Django, and the IA Go/Gin platform.

Why it was chosen. It is the default for browser and service clients, and every tool (gateways, tracing, caches) understands it.

Alternatives. gRPC for internal service-to-service calls where strict contracts and streaming matter. WebSocket for live two-way chat (Ask Iris). GraphQL when many clients need different shapes of the same data.

Likely interview questions. - "PUT versus PATCH?" PUT replaces the whole resource and is idempotent. PATCH changes some fields and may or may not be idempotent depending on the operation. - "How do you make a POST safe to retry?" The client sends an idempotency key, and the server stores it with a unique constraint. A retry with the same key returns the first result instead of doing the work twice. At Masters the bulk path used a key like client plus file hash plus batch index.

Numbers tied to it. 36 endpoints (FRM). If asked for the split: about 31 functional routes in the scoping service handler plus the collaboration-service APIs (comments and notifications) from the technical design doc.

gRPC

Depth: Skills-level. Literacy, no production ownership claim.

What it is. gRPC is a way for services to call each other's functions over the network as if they were local. You define the contract in a .proto file, and code is generated for both sides. Messages are encoded with Protocol Buffers, a compact binary format, and sent over HTTP/2. Think of a phone call where both sides read from the same printed script.

How it works. - Contract first. The .proto file defines services and message types. Code generators produce client and server stubs in many languages. - HTTP/2 transport. Many calls share one connection (multiplexing). See h2c and HTTP/2. - Four call types. Unary (one request, one response), server streaming, client streaming and bidirectional streaming. - Deadlines travel with each call, and errors use standard status codes. - Backward compatibility. You never reuse field numbers, so old and new clients can coexist.

service Scoring {
  rpc ScoreBatch (ScoreRequest) returns (ScoreResponse);
}
message ScoreRequest { repeated string article_ids = 1; string config_hash = 2; }

Where I used it. Skills-level only. My production APIs are REST and WebSocket. The IA Go edge does serve HTTP/2 over h2c, which is the same transport family gRPC uses, but I did not ship gRPC services.

When I'd pick it. For internal, high-volume service-to-service calls in a polyglot system, where strict contracts and streaming help. I would keep REST at the public edge for browsers.

Likely interview questions. - "REST or gRPC?" REST for public and browser-facing APIs, because every tool understands JSON over HTTP. gRPC for internal calls where I want generated clients, strict schemas, streaming and lower payload size. I have shipped REST in production and know gRPC at the design level. - "How does gRPC handle versioning?" By field numbers in Protocol Buffers. Celery

Depth: Skills-level. On the Skills line. No resume bullet or project Tech line names it.

What it is. Celery is a Python task queue. Your web app drops a "job ticket" on a broker (usually Redis or RabbitMQ), and separate worker processes pick it up and do the work in the background. Think of a restaurant ticket rail: the waiter clips the order, the cooks pull tickets when they are free.

How it works. - Broker, workers, result backend. The broker holds tasks. Workers run them. asyncio

Depth: Production. Impact Analytics agent plane.

What it is. asyncio is Python's built-in way to run many I/O tasks at once on a single thread. While one task waits for the network, the event loop runs another. Think of one chef with several pots on the stove, stirring whichever one needs attention instead of staring at a single pot.

How it works. - Event loop and coroutines. async def functions are coroutines. await hands control back to the loop while waiting. - asyncio.gather runs many coroutines concurrently. - asyncio.Semaphore caps how many run at once, which protects a provider's rate limit or a connection pool. - asyncio.wait_for puts a hard timeout on any await. - Never block the loop. One time.sleep or sync database call stalls everything.

sem = asyncio.Semaphore(20)                       # bounded concurrency

async def score_batch(batch):
    async with sem:
        try:
            return await asyncio.wait_for(call_llm(batch), timeout=60)
        except asyncio.TimeoutError:
            return deterministic_fallback(batch)  # graceful fallback

results = await asyncio.gather(*(score_batch(b) for b in batches))

Where I used it. Impact Analytics: the AI scoring batches run asynchronously with hard timeouts, and fall back to the deterministic score when the LLM times out (A2). "Async" here describes how batches run. The LLM never gets a database tool. The Ask Iris FastAPI WebSocket service is async too.

Why it was chosen. The workload is mostly waiting on a slow external system, the LLM provider. A thread per call would waste memory. asyncio waits cheaply.

Alternatives. Thread pools for libraries that are not async. Multiprocessing for CPU-heavy work. Go goroutines when the whole service can be in Go. In a Java service the same idea is a bounded thread pool or a non-blocking client such as Spring WebClient, which is how the Masters services kept slow IRP calls off the request thread (see Java).

Likely interview questions. - "asyncio or threads?" asyncio for many concurrent network waits with libraries that support it, because it is cheap and explicit. Threads when the library is blocking. Processes when the work is CPU-bound because of the GIL. - "How do you stop asyncio from hammering a rate-limited provider?" A semaphore caps concurrency, every call has a timeout, and retries use backoff. In AssortSmart, the orchestration registry adds a circuit breaker on top that trips after about 5 consecutive failures.

Numbers tied to it. None on its own. It supports the A2 fallback design, not a separate number.

Google Wire

What it is. Wire is a code generator for Go that does dependency injection at compile time. h2c and HTTP/2

Depth: Production. Impact Analytics C1.

What it is. HTTP/2 is the second major version of the web's protocol. It sends many requests over one connection at the same time instead of opening a connection per request. h2c means "HTTP/2 cleartext", which is HTTP/2 without TLS encryption on that hop. Think of one phone line carrying many conversations at once, with each conversation labelled so they do not mix.

How it works. - Multiplexing. Many streams share one TCP connection, so one slow response does not block the others at the HTTP layer. - Binary framing and header compression (HPACK). Smaller and faster to parse than HTTP/1.1 text. - h2c is used when TLS is handled elsewhere, for example by a cloud load balancer in front, or on internal hops. In Go you wrap the handler with h2c.NewHandler. - Nested timeouts. The server sets read, write and idle timeouts. Each request gets a deadline. Each downstream call gets a shorter deadline inside it.

h2s := &http2.Server{}
srv := &http.Server{
    Addr:              ":8080",
    Handler:           h2c.NewHandler(router, h2s),   // HTTP/2 without TLS
    ReadHeaderTimeout: 5 * time.Second,               // outer timeouts
    ReadTimeout:       30 * time.Second,
    WriteTimeout:      60 * time.Second,
    IdleTimeout:       120 * time.Second,
}
// Inner timeouts: context.WithTimeout per request, shorter ones per query.

Where I used it. Impact Analytics C1: the Go/Gin platform was deployed as a self-protecting HTTP edge without a reverse proxy, using native h2c and nested timeouts.

Why it was chosen there. Running HTTP/2 natively in the process gives multiplexing without an extra proxy hop, and keeping timeouts in the process means the service protects itself rather than relying on another layer.

Alternatives. Put Nginx or Envoy in front to handle HTTP/2, TLS and timeouts. That is a fine choice in many companies. It adds a hop and another system to run.

Likely interview questions. - "Why h2c and not TLS?" h2c is the normal choice when TLS is terminated by something in front of the process, such as a cloud load balancer, or on internal traffic. If they ask exactly where TLS ends in our deployment, answer only from what you know of the setup and do not guess. - "What are nested timeouts?" Timeouts at every layer, each shorter than the one outside it. The server's write timeout is the outer wall, the request context deadline is inside it, and each ClickHouse or Postgres query gets a shorter deadline still. A slow query fails cleanly instead of holding a connection forever.

Numbers tied to it. Part of the 10k peak RPS platform. No SLA is claimed.

WebSocket

Depth: Production. Impact Analytics A4 (Ask Iris).

What it is. A WebSocket is a long-lived, two-way connection between a browser and a server. It starts as a normal HTTP request that asks to "upgrade", and after that both sides can send messages at any time. Think of the difference between sending letters (HTTP request and response) and keeping a phone line open.

How it works. - Upgrade handshake. The client sends Upgrade: websocket. The server replies 101 Switching Protocols. - Auth happens at the handshake. Browsers cannot always set custom headers on WebSocket calls, so a token is often passed in Authorization: Bearer or as a ?token= query parameter. - Per-connection state. The server can keep session data for the life of the connection, which is powerful and risky. - Heartbeats (ping and pong) detect dead connections. - Scaling. Connections are sticky to one server, so you plan load balancing and reconnects.

If scope could be changed by a later message, a prompt or a crafted payload could pivot into another tenant's hierarchy. JWT

Depth: Production. Impact Analytics C3 and A4.

What it is. A JWT (JSON Web Token) is a small signed string that says who you are and what you can do. The server that issued it signs it, and any server that knows the signing key can check it without calling anyone. Think of a festival wristband: the organiser stamps it once, and every gate guard checks the stamp instead of phoning the office.

How it works. - Three parts: header.payload.signature, each Base64URL-encoded. The payload holds claims such as sub (user), exp (expiry), iss (issuer), aud (audience). - Signature check. With RS256 the issuer signs with a private key and you verify with its public key, often fetched from a JWKS (JSON Web Key Set) URL. - Always check signature, expiry, issuer and audience. Never accept alg: none. - Stateless trade-off. No database lookup per request, but you cannot easily revoke a token before it expires. Short expiry plus refresh tokens is the usual answer. - Not encrypted. Anyone can read the payload. Never put secrets in it.

   header (alg)          payload: {"sub":"u_42","tenant":"retailer_1","exp":1720...}

Where I used it. - Impact Analytics C3: JWT and Google OIDC are steps in the Redis-fronted auth waterfall that protects the multi-tenant platform. - Impact Analytics A4: Ask Iris verifies a JWT on the WebSocket handshake and freezes the planner's hierarchy scope from it. - My Masters India prep also describes short-lived JWT access tokens with refresh for the Spring Boot microservices. Why it was chosen. A stateless token lets the Go edge and the Python agent plane verify the same identity without a shared session store.

Alternatives. Opaque session tokens with a server-side session store (easy revocation, extra lookup). mTLS for service-to-service identity.

Likely interview questions. - "How do you revoke a JWT?" Keep access tokens short-lived and refresh them. For urgent revocation keep a small deny-list in Redis that is checked on each request. Firebase Admin and Google OIDC

Depth: Production. Impact Analytics C3.

What it is. OIDC (OpenID Connect) is a standard identity layer on top of OAuth 2.0. When a user signs in with Google, Google issues an ID token, which is a JWT that says who the user is. Firebase Admin is Google's server SDK that, among other things, verifies tokens issued by Firebase Authentication. Think of two passport offices whose stamps you trust: you check the most common one first, then the other.

How it works. - Verification. Check the token's signature against Google's published public keys, then check issuer, audience and expiry. - Waterfall. Try one verifier, and if the token is not that kind, try the next. A clear order keeps behaviour predictable. - Caching. Verifying signatures and resolving roles on every request is wasteful, so verified results are cached in Redis for a short time. - Fail closed. If a step fails or the cache misses, fall through to the source of truth. Never treat "could not check" as "allowed". - API keys for machine clients are compared in constant time, so the time taken does not leak how many characters matched.

func validKey(given, stored []byte) bool {
    return subtle.ConstantTimeCompare(given, stored) == 1
}

Where I used it. Impact Analytics C3: multi-tenant data isolation and UAM-scoped (User Access Management) hierarchy access control across PostgreSQL and ClickHouse. LangGraph

Depth: Production. Impact Analytics A4 (Ask Iris).

What it is. LangGraph is a library from the LangChain team for building LLM workflows as a graph. Each node is a step (call a model, run a check, fetch data), and edges decide which step comes next, including loops back to earlier steps. A shared state object travels through the graph. Think of a flowchart the AI walks through, with a referee who can send it back to redo a step, but only a fixed number of times.

How it works. - State. A typed dictionary (question, scope, draft answer, attempt count) passed to every node. - Nodes and conditional edges. A routing function looks at the state and picks the next node. - Cycles with caps. Loops are allowed, so you must cap them with an attempt counter and the graph's recursion limit. - Supervisor pattern. One node decides which worker should handle the request, and the workers report back. - Checkpointers can persist state between steps so a conversation can resume.

MAX_ATTEMPTS = 3

def route_after_eval(state):
    if state["passed"] or state["attempts"] >= MAX_ATTEMPTS:
        return "respond"              # stop: good answer, or out of attempts
    return "supervisor"               # try again

g = StateGraph(IrisState)
g.add_node("supervisor", supervisor)  # picks a worker
g.add_node("kpi_worker", kpi_worker)
g.add_node("evaluator", evaluator)    # checks the draft, bumps attempts
g.add_node("respond", respond)
g.add_conditional_edges("evaluator", route_after_eval)

Where I used it. Impact Analytics A4: Ask Iris runs a LangGraph supervisor with a 3-attempt evaluator loop (MAX_ATTEMPTS = 3) to prevent infinite LLM loops, with LangSmith for observability and hierarchy scope frozen at the socket handshake. LangGraph is on the IA Tech line because of this. The Keep/Drop batch does not use an LLM orchestrator. Its order is fixed in code.

Why it was chosen. A copilot needs explicit control flow: route, answer, check, maybe retry, stop. LangGraph makes the loop and its cap visible in code, instead of hiding them in a prompt.

Alternatives. Plain LangChain chains (fine for straight-line flows with no loops). A hand-written state machine (full control, more code). Multi-agent frameworks such as CrewAI or AutoGen (more autonomy, less control).

Likely interview questions. - "How do you stop an agent from looping forever?" Two caps. The evaluator loop has MAX_ATTEMPTS = 3, after which the graph returns a graceful answer instead of trying again. The graph also has a recursion limit as a backstop. Fail closed, never one more hop. - "Why a supervisor and an evaluator?" The supervisor decides which worker should answer. The evaluator checks the draft before the planner sees it. Separating them means a bad draft gets a bounded second chance instead of reaching the user. - "Why not LangGraph for Keep/Drop too?" Keep/Drop is a batch with a known order: peer, decider, lenses, blend, explain. There is nothing for an LLM to decide about the order, so a fixed pipeline is simpler, cheaper and easier to resume.

Numbers tied to it. 3-attempt evaluator loop. No usage or SLA numbers for Ask Iris.

RAG (Retrieval-Augmented Generation)

Depth: Production. Uber Menu M1.

What it is. RAG means you first retrieve relevant information, then give it to the LLM along with the question so it generates an answer grounded in that information. Think of an open-book exam: the student (the model) is smart, but you hand them the right pages before they write.

How it works. - Chunk. Split source documents into pieces small enough to embed and fit in a prompt. - Embed. Turn each chunk into a vector (a list of numbers) that captures its meaning. Similar meaning means nearby vectors. - Store and retrieve. Save vectors in a vector database. At query time, embed the input and fetch the top-k nearest chunks. - Augment and generate. Put the retrieved chunks into the prompt and call the model. - Validate. Check the output against a schema or rules before trusting it. For extraction this gate matters as much as retrieval.

New menu PDF (Italian, scanned)
  1. extract text and split into sections
  2. embed sections, search Milvus for similar menus already labelled in the catalog
  3. prompt Gemini 2.5 Pro: "Here are 5 labelled examples. Extract items, prices,
     modifiers from this menu into the catalog schema."
  4. validate the JSON against the strict catalog schema, reject or retry failures
  5. upsert into the catalog

Where I used it. Uber Menu M1: Gemini 2.5 Pro plus LangChain RAG over Milvus embeddings, converting unstructured multilingual PDFs into a strict catalog schema at 98% field fidelity on offline evaluation.

Why it was chosen. Menus vary wildly in layout and language, so regex and template rules break. Showing the model similar menus that were already labelled correctly gives it a pattern to follow, and the schema gate catches what it still gets wrong.

Alternatives. Pure OCR plus rules (brittle on new layouts). Fine-tuning a model (more expensive to keep up to date, and not on my resume). Long-context prompting without retrieval (costs more tokens and gives no examples).

Likely interview questions. - "How did you evaluate the RAG pipeline?" Offline, against labelled menus. We compared each extracted field to the correct value and measured field fidelity, which reached 98%. That is an offline number, not a live production SLA. - "RAG or fine-tuning?" RAG when knowledge or examples change often and you want to update without retraining. Fine-tuning when you need a new style or skill baked into the model. For menus, adding new labelled examples to the index was cheaper than retraining. - "What breaks RAG?" Stale or bad embeddings, retrieving the wrong examples, and trusting output without validation. The schema gate is the safety net.

Numbers tied to it. 98% field fidelity (offline). $600K per year saved: about $2 per menu in third-party or manual cost, times 30K menus, times 12 months, is $720K, floored to $600K to be conservative.

Milvus

Depth: Production. Uber Menu only.

What it is. Milvus is an open-source vector database. It stores embeddings (vectors) and finds the ones most similar to a query vector very quickly, even with very large collections. Think of a library sorted by meaning instead of by title: books about "pasta prices" sit near "Italian menu", even if they share no words.

How it works. - Collections hold vectors plus scalar metadata (for example menu_id, language, cuisine). - ANN (Approximate Nearest Neighbour) indexes. HNSW (a layered graph you hop through) or IVF (cluster vectors, then only search the nearest clusters). They trade a tiny bit of accuracy for huge speed. - Similarity metrics. Cosine, inner product or L2 (Euclidean) distance. - Filtered search. Combine "nearest vectors" with metadata filters like language == "it". - Freshness. New vectors must be inserted and indexed before they can be found.

results = collection.search(
    data=[embed(menu_section)],
    anns_field="embedding",
    param={"metric_type": "COSINE", "params": {"ef": 64}},   # HNSW search width
    limit=5,
    expr='language == "it"',
    output_fields=["menu_id"],
)

Where I used it. Uber Menu M1 only. It stored embeddings of labelled menus for the LangChain RAG pipeline with Gemini 2.5 Pro. Milvus is not part of Impact Analytics.

Why it was chosen. A dedicated vector database built for similarity search at scale, with metadata filtering, fit a large, growing collection of menu examples.

Alternatives and when I'd pick them. pgvector when the data already lives in Postgres and the collection is moderate in size. Elasticsearch or OpenSearch k-NN if a search cluster already exists. A managed vector service if the team does not want to run infrastructure.

Likely interview questions. - "HNSW or IVF?" HNSW gives fast, accurate search at the cost of more memory. IVF uses less memory and builds faster but needs tuning of how many clusters to probe. For interactive retrieval I would start with HNSW. - "Why Milvus and not pgvector?" Menu examples were a dedicated, large similarity workload, not data that needed to join with relational tables. A purpose-built vector database fit better. If it had been a small set living next to Postgres data, pgvector would have been simpler.

Numbers tied to it. Part of the 98% offline field fidelity pipeline.

pgvector

Depth: Skills-level. Literacy, no production ownership claim.

What it is. pgvector is an extension that adds a vector column type and similarity search to PostgreSQL. It lets you keep embeddings next to your normal relational data. Think of adding a "sort by meaning" drawer to a filing cabinet you already own.

How it works. - vector(n) type for an n-dimensional embedding. - Distance operators. <-> for L2, <=> for cosine distance, <#> for negative inner product. - Indexes. HNSW or IVFFlat for approximate nearest-neighbour search. - SQL joins and transactions work with vectors like any other column, which is the main advantage.

CREATE EXTENSION vector;
CREATE TABLE docs (id bigserial PRIMARY KEY, tenant_id text, body text, embedding vector(768));
CREATE INDEX ON docs USING hnsw (embedding vector_cosine_ops);

SELECT id, body FROM docs
WHERE tenant_id = 'retailer_1'
ORDER BY embedding <=> $1
LIMIT 5;

Where I used it. Skills-level only. Not used in production on any of my projects.

When I'd pick it. When the app already runs on Postgres, the vector count is moderate, and I want to filter and join vectors with relational data in one transaction. I would move to a dedicated store like Milvus when the vector workload becomes large and separate.

Likely interview questions. - "pgvector or a dedicated vector DB?" pgvector when vectors live next to relational data and the scale is moderate, because one database is simpler to run and you get joins and transactions. A dedicated database like Milvus, which I used at Uber Menu, when similarity search is a big, separate workload. - "Have you run pgvector in production?" No. It is on my skills line as literacy. My production vector work is Milvus on Uber Menu.

Numbers tied to it. None.

LLM Agents (OpenAI, Gemini, Claude)

Depth: Production for the IA lenses, Ask Iris and Menu Gemini 2.5 Pro. Claude is skills-level (no bullet ties it to a project).

What it is. An LLM (Large Language Model) is a model that reads and writes text. An LLM agent uses the model as a decision maker inside a program: it reads state, decides a step, and the program carries it out, sometimes in a loop. A structured LLM invoke is simpler: one call that must return a fixed JSON shape. OpenAI (GPT models), Google (Gemini) and Anthropic (Claude) are the main providers. Think of a very capable intern: great at judgement and language, not reliable at arithmetic, and must be supervised.

How it works. - Structured outputs. Ask for JSON that matches a schema and validate it. Never parse free text if you can avoid it. - Non-determinism. The same input can give different outputs, so you evaluate on sets of cases, not one example. - Cost and latency scale with tokens. Batching and smaller models matter at volume. - Failure handling. Provider timeouts and rate limits are normal. Hard timeouts, circuit breakers and fallbacks are required. - Keep math out of the model. Compute numbers deterministically and let the model judge patterns.

s_det   = deterministic_score(sell_through, rate_of_sale)   # pure KPI math
s_agent = decider(lens_scores)                               # 7 structured LLM lenses
s_final = 0.4 * s_det + 0.6 * s_agent
decision = "KEEP" if s_final >= 0.55 else "DROP"

Where I used it. - Impact Analytics A1: a multi-pipeline AI merchandise decision engine (Keep/Drop, Missed Opportunities, Top Style) evaluating 348k article-seasons, 88k items per pass, blending deterministic KPI math with structured LLM invokes across 7 AI lenses. An article-season is one product in one selling season. - Impact Analytics A2 and A3: the LLM never queries the 2.11B-row ClickHouse master. It gets JSON context. Timeouts fall back to the deterministic baseline, and a shared orchestration registry adds hard timeouts, circuit breakers, checkpoints and a frozen config hash. - Impact Analytics A4: Ask Iris, the LangGraph copilot. - Impact Analytics A5: model choice by benchmark. The model names (OpenAI models) are not on the PDF. - Uber Menu M1: Gemini 2.5 Pro for menu extraction. - Claude: listed as provider literacy. No resume bullet uses it. If asked, keep it general.

Why it was chosen. LLMs are good at qualitative judgement (is this style trending, does this item fit the range) and at reading messy menus. They are bad at arithmetic and expensive at volume, which is why the design wraps them in deterministic math, schemas, timeouts and fallbacks.

Alternatives. Pure rules (cheap and predictable, but miss patterns). Classical ML models (good when you have lots of labelled data for one task). For Keep/Drop we kept the rule, the deterministic score, as both a baseline and a fallback.

Likely interview questions. - "Why not let the LLM calculate KPIs?" Security, speed and correctness. A scoring agent with a code or SQL tool at 88k items is a latency and injection risk. We pre-compute KPIs and pass JSON, so the math does not depend on the model. - "What happens when the provider times out mid-run?" The batch hits its hard timeout and falls back to the deterministic score. After about 5 consecutive failures the circuit breaker trips. Checkpoints (det.json, agent_progress.json, --resume) let the run continue without redoing deterministic scoring. - "How did you pick the model?" By benchmark against the deterministic baseline. On a gold-200 set, the chosen model was 73% cheaper at 100% coverage. The blended LLM scored about 63%, below the 74% deterministic baseline, so we froze the blend weights instead of retuning them.

Numbers tied to it. 348k article-seasons, 88k per pass, 7 lenses, blend 0.4 and 0.6, keep threshold 0.55, 2.11B-row master, 73% lower cost at 100% coverage, 74% baseline. Do not say 348k is the 1.6M catalog. The $100 per pass token spend is true but off the PDF.

Tool Calling

Depth: Skills-level. My deepest tool design is verbal only (the Cluster Recommendation Copilot design), not a PDF bullet.

What it is. Tool calling (also called function calling) lets an LLM ask your program to run a named function. You describe each tool with a name and a JSON schema for its arguments. The model replies with "call get_kpis with these arguments", your code decides whether to run it, runs it, and passes the result back. Think of the model filling in a request slip, and a clerk (your code) deciding whether to act on it.

How it works. - Tool schema. Name, description and JSON Schema for arguments. - Validate arguments. Models can invent arguments. Validate types, ranges and scope before running anything. - Allowlist and read-only by default. Only expose the tools you want, and keep writes behind product APIs and explicit checks. - Scope inheritance. Tools take tenant and permission scope from the session, never from model-written arguments. - Budgets. Cap tool calls per turn and total, or a loop can burn money.

{
  "name": "get_store_kpis",
  "description": "Read-only KPIs for stores in the caller's plan scope",
  "parameters": {
    "type": "object",
    "properties": { "store_ids": {"type": "array", "items": {"type": "string"}, "maxItems": 50},
                    "season_code": {"type": "string"} },
    "required": ["season_code"]
  }
}

Where I used it. Skills-level. The design I can talk through in depth is the Cluster Recommendation Copilot design at Impact Analytics (14 tools), which is verbal only and not on the resume. The related design choice that is on the PDF goes the other way: in Keep/Drop scoring the LLM gets no SQL tool at all, and context arrives as JSON (A2).

When I'd pick it. When an assistant needs live data or actions it cannot know from the prompt, like looking up KPIs. I would not give a scoring model at batch scale any tools, because pre-computed JSON is cheaper, safer and deterministic.

Likely interview questions. - "Tool calling versus letting the model write SQL?" Typed tools are a narrow, validated interface. Free-form SQL is an open door: runaway queries, wrong joins and injection. That is why our Keep/Drop scoring LLM never gets a SQL tool against the 2.11B-row master. - "What if the model ignores the read-only instruction?" The instruction is not the control. The control is that the only tools exposed are read-only functions, scoped from the verified session.

Numbers tied to it. None on the PDF. The 14 tools figure is verbal design depth only.

MCP (Model Context Protocol)

Depth: Skills-level. Not an IA PDF bullet.

What it is. MCP is an open protocol, introduced by Anthropic, that standardises how AI applications connect to tools and data. Instead of writing custom glue for every tool in every app, a tool is wrapped once as an MCP server, and any MCP-capable host (an AI app or IDE) can use it. Think of USB-C for AI tools: one plug shape, many devices.

How it works. - Host, client, server. The host is the AI app. It runs an MCP client per connection. Each server exposes capabilities. - Three kinds of capability. Tools (functions the model can call), resources (data the app can read) and prompts (reusable templates). - JSON-RPC messages over stdio (local process) or HTTP (remote). - Discovery. The client asks the server what tools it has, with their schemas, then the model can call them through tool calling. - Security is still yours. The server must enforce auth and scope. MCP standardises the plug, not the permissions.

AI host (chat app)  --list_tools-->  MCP server "planning-data"
                    <--[get_store_kpis, get_cluster_summary]--
model decides to call get_store_kpis(season_code="S7")
host --call_tool--> server checks session scope --> returns JSON --> model

Where I used it. Skills-level only. I understand the protocol and how it relates to tool calling. It is not part of any resume bullet.

When I'd pick it. When several AI hosts (a chat app, an IDE, an internal assistant) should share the same tools without re-implementing them. For one app with a handful of tools, plain provider tool calling is simpler.

Likely interview questions. - "MCP versus plain function calling?" Function calling is how one model asks one app to run a function. MCP is a standard way to package and serve those tools so many apps can discover and use them. MCP uses tool calling underneath. - "Did you ship MCP at Impact Analytics?" It is on my skills line as literacy. My shipped IA AI work is the Keep/Drop engine and Ask Iris. I can talk through a tool design in depth, but I present it as design, not a resume claim.

Numbers tied to it. None.

Prompt Engineering

Depth: Production. Impact Analytics lenses and Uber Menu extraction.

What it is. Prompt engineering is designing the instructions, examples and output format you give an LLM so that its answers are reliable and checkable. It is closer to writing a precise spec for a contractor than to "clever wording". Think of a well-written exam question: clear task, clear format, worked example, no room for guessing what you meant.

How it works. - System versus user content. Stable rules and role go in the system prompt. Per-item data goes in the user content. - Structured output. Ask for JSON that matches a schema, and validate it. - Few-shot examples. Show the model correct examples. In RAG, retrieval picks the examples for you. - Version prompts like code. A prompt change can change results, so it must be tracked, tested and tied to outputs. - Evaluate, do not eyeball. Run every prompt change against a fixed case set.

SYSTEM: You are the "sell-through momentum" lens for retail assortment planning.
        Use only the JSON provided. Do not compute new KPIs.
        Return {"score": number 0..1, "reason": string under 40 words}.
USER:   {"article":"A-1932","season":"S7","sell_through":0.71,"rate_of_sale":3.2,
         "peer_median_sell_through":0.55}

Where I used it. - Impact Analytics A1 and A3: structured prompts for the 7 AI lenses. Prompts are part of the frozen config hash (SHA-256 of guardrails, params, prompts and catalog) stamped on every output row, so any result can be traced to the exact prompt version. - Uber Menu M1: extraction prompts that force output into the strict catalog schema, with retrieved examples from Milvus.

Why it matters. At 88k items per pass, a vague prompt does not produce one bad answer, it produces thousands. Schema-shaped prompts plus validation keep output machine-checkable.

Alternatives. Fine-tuning (bakes behaviour into weights, more cost and slower to change). Smaller task-specific models.

Likely interview questions. - "How do you version prompts?" Prompts are part of the frozen config. We hash guardrails, parameters, prompts and catalog together into a config hash and stamp it on every output row. If results change, we can see whether the prompt changed. - "Prompt engineering or fine-tuning?" Prompting first, because it is cheap to change and to test against an offline set. Fine-tuning when you have lots of labelled data and need behaviour prompts cannot reach. I do not claim fine-tuning on my resume.

Numbers tied to it. 7 lenses. 98% field fidelity on Menu (offline).

LangSmith

What it is. LangSmith is LangChain's platform for tracing, debugging and evaluating LLM applications. Every run is recorded as a tree of steps with inputs, outputs, tokens and timing. Think of a flight recorder for your AI: after a bad answer you can replay exactly what each step saw and said.

How it works. - Traces and run trees. Each graph node, model call and tool call is a child run with its own input and output. - Tokens, latency and errors per step. - Datasets and evaluations. Save real examples and re-run them after a change. - Tags and metadata (for example the graph version) to filter runs. - Low setup. For LangChain and LangGraph apps it is mostly environment variables.

Offline Evaluation

Depth: Production. Impact Analytics A5 and Uber Menu M1.

What it is. Offline evaluation means testing a model or pipeline against a fixed set of labelled cases before it reaches users, and scoring it with clear metrics. Think of a mock exam with an answer key: you only let the student sit the real exam if they pass the mock.

How it works. - Golden set. Cases with known correct answers, kept fixed so scores are comparable over time. - Metrics. Accuracy, field fidelity, coverage (how many cases got a complete answer), cost. - Baselines. Compare against the cheapest reasonable rule. If the model cannot beat it, do not ship it. - CI gate. The pipeline fails if the score drops under a threshold. - Limits. Offline is not live. A proxy set may not match every tenant, and leakage (training on test cases) inflates scores.

{ "suite": "keep_drop_proxy", "cases": 300, "gold_min_accuracy": 0.8 }

If accuracy on the 300 cases is under 0.8, the CI job fails and the change cannot be promoted.

Where I used it. - Impact Analytics A5: a 300-case proxy evaluation harness with an 80% accuracy CI gate (a promotion gate). Separately, a gold-200 benchmark compared models: the chosen model was 73% cheaper in live execution cost at 100% coverage (200 out of 200 complete). The deterministic baseline scored 74% on that set (production threshold 0.65). The blended LLM scored about 63%, under the baseline, so we froze the blend weights instead of retuning them. - Uber Menu M1: 98% field fidelity on offline evaluation of extracted menus.

Why it matters. LLM output is non-deterministic, so the only honest way to know if a change helps is to score it on the same cases every time, and to compare it with a free rule.

Alternatives. Online A/B tests (real users, slower and riskier). LLM-as-judge scoring (scales, but needs its own checks). Offline evaluation is the gate. Online monitoring confirms.

Likely interview questions. - "Does 80% mean the system is 80% accurate for all customers?" No. 80% is the CI promotion gate on a 300-case proxy set. A change cannot be promoted unless it clears it. It is not a live accuracy claim for every tenant. - "Where do 73% and 74% come from?" From a separate gold-200 benchmark, not the 300-case file. 73% is the cost reduction of the chosen model at 100% coverage. 74% is the deterministic baseline on that set. - "What did you do when the LLM lost to the baseline?" We froze the blend weights at 0.4 deterministic and 0.6 agent. We do not retune weights on a small proxy set to make a model look better than a free rule.

Numbers tied to it. 300 cases, 80% gate, 73% lower cost at 100% coverage, 74% baseline, about 63% blended (IA). 98% field fidelity (Menu). Never fuse the 300-case gate with the gold-200 numbers.

Apache Kafka

Depth: Production. Uber Menu M2 and Masters India MI2. Never Impact Analytics.

What it is. Kafka is a distributed, durable, append-only log. Producers write events to topics, and consumers read them at their own pace. Events are kept for a retention period, so consumers can re-read from any point. Think of a conveyor belt with numbered trays that keeps every tray for days: any team can read the belt, and anyone can rewind to tray 4,000 and replay.

How it works. - Topics and partitions. A topic is split into partitions for parallelism. Order is guaranteed only within a partition. - Keys. Events with the same key go to the same partition, so per-key order holds (per vendor menu, per taxpayer). - Consumer groups and offsets. Each group tracks how far it has read. Several groups can read the same topic independently. - Retention and replay. Rewind offsets to reprocess after a bug. - Delivery semantics. In practice you get at-least-once delivery, so consumers must be idempotent. Poison messages go to a dead-letter queue (DLQ) after bounded retries.

// Masters-style producer: the taxpayer GSTIN is the key, so one taxpayer's events stay in order.
String idemKey = client + ":" + fileHash + ":" + batchIndex;
kafkaTemplate.send("einvoice.bulk", clientGstin, new BulkBatch(idemKey, invoices));
// Consumer: if idemKey is already registered, skip. After bounded retries, send to the DLQ.

The Java client view (KafkaTemplate, @KafkaListener, retries and dead-letter topics) is in Spring Kafka. On Uber Menu, the consumer of the topic is the Flink job.

Where I used it. - Uber Menu M2: the ingestion bus after the Selenium fleet, feeding Apache Flink for stateful keyed deduplication (keyed by vendor and menu, using a content hash), schema normalization and exactly-once catalog upserts. - Masters India MI2: the event bus for a high-concurrency bulk e-invoicing pipeline handling 1M+ daily government submissions, with idempotent processing for 100K+ concurrent imports (idempotency key like client plus file hash plus batch index), dead-letter queues and bounded retries against volatile IRP portals. Producers and consumers were Spring Boot services using Spring Kafka. - Masters Kafka and Menu Kafka are different products at different companies.

Why it was chosen there. - Menu: scrapers are bursty and flaky. Kafka lets a scrape succeed even when the catalog or RAG step is slow, gives replay after a bad parser deploy, keeps per-vendor order, and fans out to several consumers. - Masters: filing deadlines create spikes, a 100K-invoice import cannot be one synchronous request, and double-registering an invoice with the government is not reversible. Kafka absorbs spikes and replays safely with idempotency keys.

Alternatives and when I'd pick them. RabbitMQ or SQS for simple job dispatch without replay. A job queue, or Spring @Async and scheduled jobs, for one-off background tasks. Kafka when I need a replayable, partitioned, multi-consumer log with per-key order.

Likely interview questions. - "Do you really get exactly-once?" End to end, exactly-once is mostly a slogan. In practice it is at-least-once delivery plus idempotent writes. On Menu the catalog upsert is keyed, so a replay overwrites the same row. On Masters the idempotency key with a unique constraint stops a second IRP registration. I never claim zero message loss or two-phase commit across third parties. - "Isn't 30K menus a month too small for Kafka?" The average rate is modest, and I agree. Kafka is there for its properties, not raw volume: replay after a bad parser, decoupling flaky scrapers from slow downstream steps, per-vendor order and fan-out. - "Why no Flink at Masters?" Masters did not need stateful windowing or late-event deduplication. Idempotent consumers and PostgreSQL were enough. Menu needed keyed state for duplicate and late pages.

Numbers tied to it. Masters: 1M+ daily submissions, about 12 TPS average (1,000,000 divided by 86,400), peaks ESTIMATED at 8 to 10 times that around filing deadlines, 100K+ concurrent imports. Menu: 30K+ menus per month. A peak of about 200 to 500 events per second on Menu is an ESTIMATE for prep only, do not volunteer it.

Spring Kafka

Depth: Production. Masters India MI2 (the Java client side of the Masters Kafka pipeline).

What it is. Spring for Apache Kafka (usually called Spring Kafka) is Spring's integration with the Kafka Java client. It gives you KafkaTemplate to publish and @KafkaListener to consume, and it handles the consumer loop, offsets, retries and dead-letter routing for you. Think of a post room for a building: you drop a letter in the outgoing tray or name the mailbox you want to watch, and the post room handles the trucks and the sorting.

How it works. - KafkaTemplate.send(topic, key, value) publishes. The key decides the partition, so the same key keeps its order. - @KafkaListener(topics, groupId) turns a method into a consumer in a consumer group. concurrency sets how many consumer threads run, and more threads than partitions just sit idle. - Acknowledgement mode. Offsets are committed after the listener succeeds, so a crash replays the record. Delivery is at least once, which is why the handler must be idempotent. - DefaultErrorHandler retries a failing record with a back-off, then hands it to a DeadLetterPublishingRecoverer, which writes it to a dead-letter topic (DLT) so one poison message cannot block the partition. - Serializers (JSON or Avro) turn objects into bytes and back.

@Configuration
class KafkaErrorConfig {
    @Bean
    DefaultErrorHandler errorHandler(KafkaTemplate<String, Object> template) {
        var recoverer = new DeadLetterPublishingRecoverer(template);   // -> einvoice.bulk.DLT
        return new DefaultErrorHandler(recoverer, new FixedBackOff(2000L, 3L)); // bounded retries
    }
}

@Component
class BulkBatchConsumer {
    @KafkaListener(topics = "einvoice.bulk", groupId = "irp-submitter")
    void onBatch(BulkBatch batch) {
        if (registry.alreadyProcessed(batch.idemKey())) {
            return;                                   // replay or duplicate: do nothing
        }
        irpService.submit(batch);                     // may throw, handled by the error handler
        registry.markProcessed(batch.idemKey());      // unique constraint on idemKey
    }
}

Where I used it. Masters India MI2: the Spring Boot producers and consumers on the Kafka event bus of the bulk e-invoicing pipeline. Idempotency keys (client plus file hash plus batch index) with a unique constraint, dead-letter queues and bounded retries against volatile IRP portals. Uber Menu's Kafka consumers are the Flink job, not Spring Kafka.

Why it was chosen there. The services were already Spring Boot, so Spring Kafka gave consumers, retries and DLQ routing as configuration instead of a hand-written poll loop. It also plugged into the same tracing and logging as the rest of the service.

Alternatives and when I'd pick them. The plain Kafka Java client when I need full control of the poll loop. Kafka Streams for stateful stream processing inside the JVM. Flink for heavy stateful processing with event time, which is what Uber Menu used.

Likely interview questions. - "How do you build a dead-letter queue in Spring Kafka?" Configure a DefaultErrorHandler with a bounded back-off and a DeadLetterPublishingRecoverer. A failing record is retried a few times, then published to a dead-letter topic with the error in its headers, and the consumer moves on. Someone can inspect and replay the DLT later. - "Why must the consumer be idempotent?" Offsets are committed after processing, so a crash or rebalance between "IRP accepted it" and "offset committed" replays the record. The idempotency key with a unique constraint makes that replay a no-op instead of a second government registration. - "How many consumer threads should you run?" At most the number of partitions in the topic for that group, because each partition is read by one consumer at a time. To scale further you add partitions, and you choose keys so load spreads evenly.

Numbers tied to it. 1M+ daily submissions (about 12 per second on average, peaks ESTIMATED at 8 to 10 times that around filing deadlines) and 100K+ concurrent imports, as for Apache Kafka.

Apache Flink

Depth: Production. Uber Menu M2 only.

What it is. Flink is a stream processor. It reads events continuously (here from Kafka), keeps state per key, and processes each event as it arrives instead of waiting for a nightly batch. Think of a sorting clerk standing at the conveyor belt who remembers every tray he has already seen and throws away duplicates.

How it works. - Keyed streams and keyed state. keyBy(vendor_menu_id) sends all events for one key to the same task, which keeps a small memory (for example "last content hash seen") for that key. - Event time and watermarks. Events can arrive late or out of order. A watermark says "I have probably seen everything up to time T", which bounds how long you wait. - Checkpoints. Flink periodically snapshots all state and Kafka offsets together. After a crash it restores and replays from there. - Exactly-once state, idempotent sink. Checkpoints give exactly-once state. The external write (the catalog) must still be idempotent. - State TTL expires old keys so state does not grow forever.

# Pseudocode for keyed deduplication
class DedupeMenu(KeyedProcessFunction):            # keyed by vendor/menu id
    def process_element(self, event, ctx):
        last = self.last_hash.value()               # per-key state
        if last == event.content_hash:
            return                                  # duplicate page, drop it
        self.last_hash.update(event.content_hash)
        yield normalize_to_catalog_schema(event)    # then idempotent upsert

Where I used it. Uber Menu M2 only: a large-scale ingestion and processing pipeline on Kafka and Apache Flink with stateful keyed deduplication (keyed by vendor and menu, content hash), schema normalization and exactly-once catalog upserts. Not at Masters, not at Impact Analytics.

Why it was chosen there. Scrapes are bursty and retried, so the same menu can arrive several times or late. Flink's keyed state drops duplicates, event time handles late pages, and continuous processing kept catalog freshness in hours instead of a day.

Alternatives and when I'd pick them. Plain Kafka consumers for stateless transforms. Spark for big historical backfills (verbal only, not on my resume). Kafka Streams if everything stays inside Kafka and in the JVM.

Likely interview questions. - "Why Flink and not plain consumers?" Plain consumers are fine for fire-and-forget transforms. We needed per-vendor state for deduplication, event time for late pages, and one job that validates, deduplicates and normalizes before the upsert. That is Flink's sweet spot. - "Why not Spark?" Spark Structured Streaming works in micro-batches and is heavier for per-key state on a freshness-sensitive path. I would use Spark for large backfills. It is not on my resume. - "A bad parser shipped. How do you recover?" Stop the job, fix the code, rewind Kafka offsets to before the bad deploy and reprocess. Because the catalog upsert is idempotent, replaying overwrites rows instead of duplicating them.

Numbers tied to it. Extraction success 95%+ (from an estimated 60 to 65%), 30K+ menus per month, onboarding from 24 hours to 2 hours. No measured Flink throughput is claimed.

ClickHouse

Depth: Production. Impact Analytics A2, C2, C3, C4, C5. My deepest data technology.

What it is. ClickHouse is a columnar OLAP (Online Analytical Processing) database built for fast aggregations over billions of rows. Normal databases store data row by row. ClickHouse stores each column separately, so summing one column reads only that column, and similar values compress very well. Think of a spreadsheet stored by columns: to total the "revenue" column you lift out one strip of paper instead of reading every row.

How it works (the big ideas). - Columnar storage and compression. Queries read only the columns they touch. - The MergeTree family of table engines (explained below). - Partitions for managing data in big chunks. - Mutations are expensive. ALTER TABLE ... UPDATE rewrites data in the background. ClickHouse prefers inserts over in-place updates. - Aggregation memory. A big GROUP BY holds its state in RAM. Without limits and spill-to-disk, it can run out of memory.

MergeTree

What it is. MergeTree is ClickHouse's main table engine. Each insert writes a sorted, immutable chunk called a part. Background merges combine small parts into bigger ones. Think of a stack of sorted index cards: you drop new sorted bundles on top, and an assistant periodically merges bundles into bigger sorted bundles.

  • ORDER BY sets the sort key, which is also the sparse primary index. It stores one index entry per block of rows (a granule, 8,192 rows by default), so it is tiny and lets ClickHouse skip blocks that cannot match.
  • PARTITION BY groups parts by a value, like season.
  • Big batched inserts are good. Many tiny inserts create too many parts.
CREATE TABLE product_season (
    season_code   UInt16,
    product_id    String,
    store_count   UInt32,
    revenue       Float64,
    units_sold    Float64
) ENGINE = MergeTree
PARTITION BY season_code
ORDER BY (product_id);

ReplacingMergeTree

What it is. ReplacingMergeTree is a MergeTree variant that keeps only the newest version of rows with the same sort key. Duplicates are removed during background merges, not at insert time. Think of a notebook where you never erase: you write the new value below the old one, and a cleaner later crosses out the old lines.

  • A version column decides which row wins.
  • Until a merge runs, duplicates can still be visible. Correct reads use argMax(value, version), LIMIT 1 BY key, or FINAL (slower).
  • This makes retries safe: writing the same article twice just leaves the newer version.
CREATE TABLE keep_drop_score (
    article_id String, season_code UInt16,
    s_final Float64, decision String, config_hash String,
    version UInt64
) ENGINE = ReplacingMergeTree(version)
ORDER BY (season_code, article_id);

-- Read the latest decision per article without waiting for merges
SELECT article_id, argMax(decision, version) AS decision
FROM keep_drop_score WHERE season_code = 7 GROUP BY article_id;

Partitions

What they are. A partition is a big, separately managed slice of a table, chosen by PARTITION BY. You can drop, replace or move a whole partition as one operation, and queries that filter on the partition key skip other partitions entirely. Think of a filing cabinet with one drawer per season: you can empty or refill one drawer without touching the others.

  • Partition pruning. WHERE season_code = 7 reads only drawer 7.
  • ALTER TABLE ... DROP PARTITION 7 removes a season instantly. That is how a half-copied season was cleaned before recopying.
  • Keep the count moderate. Too many partitions means too many parts.

Native protocol

What it is. ClickHouse speaks two protocols. HTTP (port 8123, or 8443 with TLS) is easy to use from anything. The native protocol (port 9000, or 9440 with TLS) is a binary, columnar protocol used by ClickHouse's own client and drivers such as clickhouse-go. It is faster for bulk data because blocks of columns travel as-is. Think of shipping goods in sealed pallets instead of unpacking them into individual parcels.

batch, _ := conn.PrepareBatch(ctx, "INSERT INTO attr_weekly")
for _, row := range rows {          // in practice: columnar appends, 500k rows per batch
    batch.Append(row...)
}
batch.Send()                         // one columnar block over native TLS (port 9440)

ETL Pipelines

Depth: Production. Uber FRM, Uber Menu, Masters India, Impact Analytics.

What it is. ETL means Extract, Transform, Load: pull data from a source, clean and reshape it, and write it to a target. ELT is the same idea but you load first and transform inside the target database. Think of a water treatment plant: take water from the river, filter it, and pipe it to homes.

How it works. - Batch or streaming. Nightly or chunked jobs versus continuous processing (Kafka plus Flink). - Idempotent reruns. Running a step twice must give the same result. Natural keys, upserts and "drop partition then reload" achieve that. - Checkpoints and ledgers. Record which chunks finished so a restart skips them. - Data quality checks. Row counts, sums and schema checks between source and target. - Locking and contention. Loads that update shared tables can block users, so schema and transaction design matter.

FRM example
Extract:   raw GL (general ledger) rows that used to live in Google Sheets
Transform: map accounts to the 4-level FSLI hierarchy (L1-L4), annualize by quarter,
           compute significance against materiality
Load:      upsert into MySQL tables keyed by SHA-256 natural keys, in one transaction

Where I used it. - Uber FRM F1 and F2: the Sheets-to-MySQL migration across 19M raw GL rows, and resolving ETL lock contention during financial close with an 8-table normalized schema, optimistic row-locking and atomic cross-table syncs. The HFM (Oracle Hyperion) extract was a shared pipeline responsibility. - Uber Menu M2: the Kafka plus Flink ingestion and processing pipeline. - Masters India MI2: the bulk e-invoicing import pipeline, with chunked, idempotent batches processed by Spring Boot services. - Impact Analytics C4 and C5: rollup builds with temporal-chunked INSERT SELECT, and the cross-cluster copy with ledgers and checkpoints.

Why it matters. My ETL stories are about correctness and restartability, not just speed: no duplicate audit rows, no ghost rows after a crash, no lock fights during close.

Alternatives. Orchestrators like Airflow or Temporal for scheduling and retries. Spring Batch for chunked, restartable jobs inside a Java service. At Impact Analytics we chose application-native checkpoints because resume logic was tied to ClickHouse inserts and config hashing, so extra infrastructure was not justified.

Likely interview questions. - "How do you make an ETL rerun safe?" Every write is keyed so it can be repeated: SHA-256 natural keys on FRM, idempotency keys at Masters, ReplacingMergeTree and partition reloads at Impact Analytics. A ledger records finished chunks, and an unfinished chunk is cleaned and redone, not appended to. - "What was the FRM lock contention?" During financial close, the ETL load and finance users were touching the same data. Normalizing into 8 tables, using optimistic row-locking (a version check on update) and doing cross-table syncs in one transaction removed the contention.

PostgreSQL

Depth: Production. Impact Analytics C3 and Masters India MI2.

What it is. PostgreSQL (Postgres) is an open-source relational database known for correctness, rich SQL and extensions. It is the default choice for transactional data, where every change must be safe and consistent. Think of a meticulous accountant's ledger: every entry balanced, nothing half-written.

How it works. - ACID transactions. Atomic, Consistent, Isolated, Durable. A transaction fully happens or not at all. - MVCC (Multi-Version Concurrency Control). Readers see a snapshot and do not block writers. Old row versions are cleaned by VACUUM. - Indexes. B-tree for equality and ranges, GIN for JSONB and full-text, partial indexes for hot subsets. - Partitioning and sharding. Declarative partitioning splits a table by range or list. Sharding spreads data across separate databases or nodes. - Connection pooling. Postgres uses a process per connection, so an application pool like HikariCP, and sometimes a server-side pooler like PgBouncer, protect it under load.

-- Range partitioning by tax quarter (illustrates the idea behind quarter sharding)
CREATE TABLE invoice_header (
  invoice_id text, client_gstin text, invoice_date date, period_quarter text
) PARTITION BY LIST (period_quarter);

CREATE TABLE invoice_header_2024q1 PARTITION OF invoice_header FOR VALUES IN ('2024Q1');
CREATE TABLE invoice_header_2024q2 PARTITION OF invoice_header FOR VALUES IN ('2024Q2');

Where I used it. - Impact Analytics C3: the thin transactional layer for tenant metadata, UAM and roles. Role resolution in the auth waterfall is Postgres-backed. Planner facts moved to ClickHouse after proof-of-concept tests showed Postgres was too slow for large pivots. - Masters India MI2: PostgreSQL horizontally sharded by tax quarter for the bulk e-invoicing pipeline. Routing derives the quarter from the invoice date. The Spring Boot services reached it through Hibernate and a HikariCP connection pool.

Why it was chosen there. Identity, roles and invoices need real ACID guarantees. GST work is quarter-scoped, so sharding by quarter keeps the hot current-quarter writes separate from cold history.

Alternatives. MySQL (similar role, chosen where it is the company standard, as at Uber). ClickHouse for big analytical reads. MongoDB when the document shape varies a lot.

Likely interview questions. - "Why shard by tax quarter?" GST filings are quarter-scoped, so most reads and writes hit the current quarter. Sharding by quarter isolates hot writes, keeps indexes small, and lets old quarters be archived without touching live traffic. The risk is cross-quarter queries, which become fan-out reads. - "Why keep Postgres at Impact Analytics if ClickHouse is faster?" ClickHouse is fast for aggregations but weak at small transactional updates. Users, tenants, roles and access rules need ACID, so Postgres keeps them and ClickHouse holds the facts. - "How does MVCC work?" Each update writes a new row version. Each transaction sees the versions that were committed when its snapshot started. So readers never block writers, and VACUUM later removes versions nobody can see.

Numbers tied to it. 1M+ daily submissions, 100K+ concurrent imports (Masters). From 189 seconds to 12 seconds once pivots moved off Postgres to ClickHouse rollups (IA, a ClickHouse number).

MySQL and Uber SOADB

Depth: Production. Uber FRM F1, F2, F3 and GeeksforGeeks.

What it is. MySQL is a widely used open-source relational database. Its main storage engine, InnoDB, gives transactions, row-level locks and MVCC. SOADB is Uber's service-owned MySQL standard: each service owns its own MySQL database under a common platform. Think of MySQL as a well-organised shared office, and SOADB as each team getting its own office on the same managed floor.

How it works. - InnoDB row locks. Updates lock only the rows they touch, but long transactions still block others. - Optimistic locking. Instead of locking up front, each row carries a version. An update only succeeds if the version is unchanged. Otherwise the user is told someone else edited first. - Unique constraints and natural keys stop duplicates at the database level. - Transactions across tables keep related changes in sync. - Normalization splits data into tables with one job each, so updates touch less and conflict less.

-- Optimistic row-locking: succeed only if nobody changed the row since I read it
UPDATE scoping_assessments
SET status = 'Review', version = version + 1
WHERE uuid = :uuid AND version = :version_i_read;
-- 0 rows updated means conflict: reload and retry, or tell the user.
-- With Hibernate, a @Version field on the entity generates exactly this WHERE clause.

// Deterministic SHA-256 natural key: the same question on the same page always gets the same id
static String naturalKey(String questionText, String pageName) throws NoSuchAlgorithmException {
    MessageDigest sha = MessageDigest.getInstance("SHA-256");
    byte[] hash = sha.digest((questionText + normalize(pageName)).getBytes(StandardCharsets.UTF_8));
    return HexFormat.of().formatHex(hash);
}

Where I used it. - Uber FRM F1: the Sheets-to-MySQL migration across 19M raw GL rows, behind 36 Spring Boot endpoints. - Uber FRM F2: an 8-table normalized MySQL schema on Uber's SOADB with a polymorphic review-status model (one status model reused across screens: Draft, Review, ReOpen, Closed), optimistic row-locking (@Version in Hibernate), atomic cross-table syncs (@Transactional) and SHA-256 natural keys to stop duplicates across quarterly audit trails. - Uber FRM F3: the Spring Data JPA / Hibernate migration on top of it. - GeeksforGeeks: MySQL as the relational store for users, votes and subscriptions, through Django. - Verbal depth for FRM: there are 11 ORM entity models in the scoping service code, while the PDF's "8-table schema" is the normalized design in F2. If asked, say both clearly.

Why it was chosen there. At Uber, SOADB is the standard store for services, so MySQL was the natural system of record once data moved off Sheets. Optimistic locking fits finance review work, where conflicts are rare but must never silently overwrite.

Alternatives. Pessimistic locking (SELECT ... FOR UPDATE, or @Lock(PESSIMISTIC_WRITE) in JPA) when conflicts are frequent. PostgreSQL in companies where it is the standard. A warehouse alone was rejected, because finance needed transactional edits and an audit trail.

Likely interview questions. - "Optimistic or pessimistic locking?" Optimistic when conflicts are rare and you do not want users holding locks, which fits finance reviewers working on different lines. Pessimistic when many writers fight over the same row. With optimistic locking, a stale update fails cleanly and the user reloads. - "Why SHA-256 natural keys?" So the same logical record always gets the same id, quarter after quarter. A re-import cannot create a duplicate because the key collides with the unique constraint. Example: uuid equals SHA-256 of the question text plus the normalized page name. - "What is a polymorphic review-status model?" Redis

Depth: Production. Impact Analytics C3, Masters India MI3, GeeksforGeeks.

What it is. Redis is an in-memory key-value store. It is extremely fast because data lives in RAM, and it supports rich types like counters, lists, sets and sorted sets, each with an optional expiry (TTL). Think of sticky notes on your monitor: instant to read, but you would not keep your only copy of a contract there.

How it works. - Cache-aside. The app checks Redis first. On a miss it reads the database, then writes the result to Redis with a TTL. - TTL and invalidation. Expire keys after a time, or delete them when the source changes. - Stampede protection. When a hot key expires, thousands of requests can hit the database at once. A short lock or jittered TTL prevents that. - Atomic operations like INCR make counters safe under concurrency. - Not the source of truth. If Redis is lost, the app must still work from the database.

// Masters-style cache-aside in a Spring Boot service (Spring Data Redis).
public ClientConfig getClientConfig(String gstin) {
    String key = "cfg:" + gstin;
    ClientConfig cached = redis.opsForValue().get(key);
    if (cached != null) {
        return cached;
    }
    ClientConfig cfg = configRepo.findByGstin(gstin).orElseThrow();   // miss: source of truth
    redis.opsForValue().set(key, cfg, Duration.ofMinutes(5));          // cache for 5 minutes
    return cfg;
}

Spring's @Cacheable("clientConfig") on the method does the same thing with less code, and @CacheEvict on the update path removes the stale entry.

Where I used it. - Impact Analytics C3: Redis fronts the auth waterfall so verified identities are not re-checked against Firebase or OIDC on every request. A miss falls through to real verification and Postgres. It never fails open. - Masters India MI3: a Redis cache-aside layer in the Spring Boot services that, together with ELK and New Relic work, lowered database read load by 30%. Redis was also part of the p95 latency win. - GeeksforGeeks: caching and hot counters for the doubt-support platform during contest spikes.

Why it was chosen there. The same data (verified tokens, client config) was read on almost every request. Caching it in memory removed repeated database reads.

Alternatives. An in-process cache (fastest, but each server has its own copy). Memcached (simpler, fewer data types). A CDN for public static content.

Likely interview questions. - "How do you handle cache invalidation?" Short TTLs for data that can be slightly stale, and explicit deletes on write for data that cannot. The database stays the source of truth, so a wrong cache entry expires instead of living forever. - "What if Redis goes down?" Requests fall through to the database. Load goes up, but correctness holds. For auth we never treat a Redis failure as permission. - "What is a cache stampede?" A hot key expires and every request misses at once, hammering the database. Fixes are a lock so only one request refills the key, jittered TTLs, or refreshing before expiry.

Numbers tied to it. Database read load cut by 30% (Masters, together with the tracing work in the same bullet).

Docker

What it is. Docker packages an application with everything it needs (runtime, libraries, config) into an image, which runs as an isolated container on any machine. Think of a shipping container: whatever is inside, every crane and ship handles it the same way.

Maven

Depth: Skills-level. On the Skills line. No resume bullet names it. FRM built with Bazel.

What it is. Apache Maven is the standard build and dependency tool for Java projects. One file, pom.xml, declares the project, its dependencies and its plugins, and Maven downloads the libraries, compiles, tests and packages the result. Think of a recipe card plus a pantry service: you list the ingredients and steps, and the pantry delivers the exact versions you asked for.

How it works. - POM (Project Object Model). pom.xml holds coordinates (groupId, artifactId, version), dependencies and plugins. - Lifecycle phases. validate, compile, test, package, verify, install, deploy. Running a phase runs every phase before it. - Dependency scopes. compile, test, provided, runtime. Test libraries such as JUnit stay out of the shipped jar. - Dependency management and BOMs. A BOM (Bill of Materials), such as the Spring Boot parent, pins compatible versions of many libraries at once. - Conflict resolution. When two libraries need different versions of a third, Maven picks the one nearest to your project in the dependency tree. mvn dependency:tree shows what you actually got. - Plugins. Surefire runs unit tests, JaCoCo measures coverage, and the Spring Boot plugin builds the runnable fat jar.

Selenium

Depth: Production. Uber Menu M2.

What it is. Selenium automates a real web browser from code: open pages, click, scroll, wait for content and read the result. It is used for testing websites and for collecting data from sites that need a real browser because content loads with JavaScript. Think of robot hands on a keyboard and mouse that do exactly what a person would do, but tirelessly.

How it works. - WebDriver controls Chrome or Firefox, often headless (no visible window). - Explicit waits wait for an element to appear instead of sleeping a fixed time. - Selectors (CSS or XPath) find elements. Many browser workers run in parallel, with monitoring for failure rates.

def fetch_menu(url, attempt=0):
    driver = new_driver(proxy=proxy_pool.next())          # dynamic proxy pool
    try:
        driver.get(url)
        WebDriverWait(driver, 20).until(EC.presence_of_element_located((By.CSS_SELECTOR, ".menu")))
        return driver.page_source
    except TimeoutException:
        if attempt < 4:
            time.sleep(min(2 ** attempt + random.random(), 30))   # adaptive backoff
            return fetch_menu(url, attempt + 1)
        raise
    finally:
        driver.quit()
