Part A: Uber FRM (Financial Risk Management) Scoping Platform

A1. The 30-second and 2-minute versions

30 seconds. "At Uber, via EPAM, I owned the FRM scoping backend for Uber Finance, a Spring Boot and MySQL platform that replaced a quarterly Google Sheets close. It cut quarterly reconciliation by 70%, from 14 days to 3 days, against a $340M materiality threshold. I migrated 19 million raw general-ledger rows off Sheets, shipped 36 Spring Boot endpoints for the financial math and a four-level line-item hierarchy with quarter-annualization, designed an 8-table normalized schema with optimistic locking and SHA-256 natural keys, and led 3 engineers on a Spring Data JPA / Hibernate migration that took module statement coverage to 100%."

2 minutes. "Scoping is a SOX compliance process that runs every quarter during the financial close. Finance decides which balance-sheet and income-statement lines, and which legal entities, PwC will test. Before the tool it was a Sheets workbook with no stable line IDs, no audit trail and constant overwrite risk. I owned the backend replacement: a Spring Boot controller, service and repository layering over MySQL on Uber's SOADB standard. Uber's gateway injects the user's email in a header and every write records it, so every decision is attributable.

The rules are deterministic Java service code with exact BigDecimal money math. A line is quantitatively material if its HFM amount is above materiality, $340 million on the Q4 2025 close. It's qualitatively material if a manager flags it on a scoping question. It's significant if either is true. Components are significant if they carry more than 5% of revenue or assets. Residual risk measures what's left uncovered in multiples of materiality. Part-year income figures are annualized so they compare fairly.

For integrity during close, I designed an 8-table normalized schema with a shared Draft, Review, ReOpen, Closed status model, optimistic row-locking through a JPA @Version column, atomic cross-table writes inside @Transactional service methods, and SHA-256 natural keys so reloads never duplicate audit rows. I also migrated reconciliation from Sheets-backed v1 endpoints to MySQL-backed v2 endpoints running in parallel. Then I led 3 engineers through a Spring Data JPA / Hibernate migration that removed a silent column-aliasing bug class, reached 100% statement coverage on those modules, and shipped as stacked Bazel PRs with SOX gates. Reconciliation went from 14 days to 3."

A2. Finance in 90 seconds

Full explanations with worked examples are in the FRM deep dive, section 3. The short version:

  • Close: the period-end routine that finalises a quarter's books. Scoping runs inside it, against a deadline.
  • GL (general ledger): the master record of every account balance per entity per period. Individual quarterly extracts were about 38K to 95K rows (MEASURED). The resume's 19M is the total raw GL migrated off Sheets (PDF).
  • HFM vs 10-Q: HFM (Oracle Hyperion Financial Management) is the consolidation system. The 10-Q is the quarterly SEC filing. Reconciliation checks they agree per line: difference = hfm_amount_in_millions - financial_statement_amount_in_millions.
  • FSLI, L1 to L4: a Financial Statement Line Item is one line like Cash or Revenue. Lines nest four levels deep, for example Assets, then Current assets, then Cash and cash equivalents, then Cash in bank. A parent must equal the sum of its children.
  • Materiality, $340M: the size of a mistake that would matter to a reader. Illustrative: Cash at $6,120M is above $340M, so it's quantitatively material. Prepaid expenses at $95M is not, unless a manager flags it qualitatively.
  • Scoping and the 5% rule: group scoping asks "is this line significant to Uber?". Component scoping asks "which entities under it get tested?". A component is financially significant if revenue share is over 5% or absolute assets share is over 5%.
  • Residual risk: residual balance = HFM amount minus total in scope. Residual multiple = residual balance / materiality. Illustrative: $200M left uncovered is 0.59 × $340M, over 50%, so it's flagged. The residual threshold on Q4 2025 was $170M.
  • Quarter-annualization: scaling part-year income-statement figures to a full-year equivalent, for example × 4/2 at the end of Q2, so they compare fairly with annual thresholds.
  • SOX and PwC: SOX (Sarbanes-Oxley) makes management responsible for financial controls and has the external auditor, PwC, test them. In engineering terms: traceable numbers, attributable changes, repeatable and evidenced controls.

Walkthrough. HFM-loaded data lands in MySQL through a shared ETL that I consume but did not own end to end. The gateway authenticates the user and adds the x-auth-params-email header. The @RestController (the class whose methods answer HTTP requests) validates input with Bean Validation (@Valid plus annotations like @NotNull on request DTOs), and one @RestControllerAdvice maps exceptions to status codes, for example a failed version check to 409. The @Service classes apply the finance rules, build the trees and own the @Transactional boundaries, so each multi-table write commits or rolls back as one unit. Spring Data JPA repository interfaces own every query, with Hibernate generating the SQL. Spring MVC runs each request on its own server thread, so blocking database calls need no special handling, and connections come from a shared HikariCP pool. The screens (Reconciliation, Materiality, EMI Scoping, Group Scoping, Threshold Setup, Component Scoping, Residual Risk, Summary) call the API. I owned the backend, not the React UI.

Multi-table edits One @Transactional service method per sync All-or-nothing, no half-applied decisions Slightly longer transactions

Recon cutover Parallel v1 Sheets + v2 MySQL Zero downtime, side-by-side QA Two paths until the UI cutover

Releases Stacked Bazel PRs Small, reviewable, each tested, zero downtime More PRs to sequence

The main alternative questions: PostgreSQL was rejected because the platform standard was MySQL and the hierarchy is flattened anyway. Pessimistic locking was rejected because it would block the ETL and other editors for the whole time someone has a record open. A big-bang rewrite was rejected in favour of stacked PRs and a parallel v2 path.

A5. Each bullet decoded

F1: ownership, 70%, 19M, 36 endpoints

Owned the Financial Risk Management scoping backend, reducing quarterly reconciliation time by 70% (from 14 days to 3 days) against a $340M materiality threshold. Engineered the Sheets-to-MySQL migration across 19M raw GL rows, shipping 36 Spring Boot endpoints to automate custom financial math and a nested 4-level FSLI (L1–L4) hierarchy with dynamic quarter-annualization.

  • In plain words: I owned the server side. The close's reconciliation went from two weeks of spreadsheet work to three days. Data moved from Sheets to MySQL, and 36 endpoints now do the math that used to be spreadsheet formulas.
  • Own: backend design and architecture of the scoping service. The ETL was shared. The collaboration service was separate. The UI was not mine.
  • 36, if asked: about 31 functional routes in the scoping service controller (32 request-mapping methods including /health) plus the collaboration-service comment and notification APIs from the design doc.
  • 19M, if asked: raw GL rows migrated off Sheets. Per-quarter extracts were tens of thousands of rows, so the value was correctness, hierarchy and auditability, not throughput.
  • 70%, if pressed: "The technical design doc framed that cut and that's what the platform delivered for the close." If someone does the arithmetic, 14 to 3 days is about 79%, so 70% is the conservative figure.

F2: schema and integrity

Resolved ETL pipeline lock contention during financial close by designing an 8-table normalized MySQL schema on Uber's SOADB featuring a polymorphic review-status model. Guaranteed real-time, multi-user collaboration integrity by implementing optimistic row-locking, atomic cross-table syncs, and deterministic SHA-256 natural-key hashing to eliminate data duplication across quarterly audit trails.

  • In plain words: the ETL and the managers both hit the data during close. Narrow normalized tables plus short transactions plus optimistic locks mean they rarely block each other. Multi-table updates are all-or-nothing, and content-derived IDs stop duplicates.
  • Polymorphic review-status: one status vocabulary (Draft, Review, ReOpen, Closed) reused on group_status, component_status, residual_status and the threshold table's review_status.
  • Optimistic row-locking: the entity has a @Version field, so Hibernate sends UPDATE ... WHERE uuid = ? AND version = ? and bumps the version. Zero rows updated means someone else saved first: Hibernate throws OptimisticLockException, the transaction rolls back, and the API returns 409 so the screen reloads. The client also sends back the version it read, so the check covers the manager's think time, not just the request.
  • Atomic syncs (real code): the EMI Total patch mirrors into balance_sheet or income_statement inside one @Transactional service method. An assessment write with sync_required throws, and so rolls back, if the line sync touches zero rows. Spring rolls back by default only on unchecked exceptions, and only when the method is called through the Spring proxy (not from inside the same class).
  • SHA-256 natural keys (real code): scoping_questions.uuid = SHA-256 of question_text + normalized page_name, upserted by the bulk endpoint. In Java that is MessageDigest.getInstance("SHA-256") over the UTF-8 bytes, hex-encoded:
MessageDigest sha = MessageDigest.getInstance("SHA-256");
byte[] hash = sha.digest((questionText + normalizedPage).getBytes(StandardCharsets.UTF_8));
String uuid = HexFormat.of().formatHex(hash);   // same question + page, same 64-char ID
  • 8 vs 11, if asked: 8 is the core normalized schema. The scoping service code has 11 JPA entity classes, including supporting tables such as the recon v2 leaves and the metrics store.
  • Careful: "real-time collaboration integrity" means the integrity of concurrent writes. The real-time push and Slack notifications were the separate collaboration service and the frontend.

F3: leadership, ORM migration, SOX gates

Led 3 engineers in a core Spring Data JPA / Hibernate migration that eliminated latent column-aliasing bugs and raised module statement coverage to 100%. Orchestrated zero-downtime releases via stacked Bazel PRs, embedding reporting SQL allowlists and automated FSM gates with 50% delta-variance checks to enforce SOX compliance.

  • In plain words: native SQL results were copied into maps keyed by column label, which broke silently on joins. I led a pod of 3 moving that code to @Entity classes and Spring Data JPA repository queries with explicit aliases and typed projections, tested to 100% statement coverage on the migrated modules, shipped in small stacked PRs. Reporting queries were limited to an approved list, and status changes were gated on large swings.
  • Own: tech lead of a 3-engineer EPAM pod, not a people manager. API contracts and layered design reviews.
  • FSM gate: the Draft, Review, ReOpen, Closed state machine. On a transition, a line whose amount moved more than 50% against its comparison value cannot silently advance. Keep the exact formula qualitative.
  • Tests: 1,100+ JUnit 5 tests (VERBAL, a count of @Test methods finds about 1,288). Controllers are tested with MockMvc (fake HTTP requests against the web layer only) and Mockito mocks of the services. Services are tested with mocked repositories. Each package runs as a Bazel java_test target that must pass before merge.

A7. Hard problem in one paragraph: the column-aliasing bug

The legacy read path ran native SQL and copied each result row into a Map keyed by column label. A join of a fact table and level_mapping returned two columns both labelled uuid. The loop puts them in order and the map keeps the last value, so each row silently took the mapping's ID instead of the fact's ID. Edits and comments then pointed at the wrong line, which is how it surfaced: editing one recon line seemed to change another. The fix was Spring Data JPA @Query methods with an explicit, unique alias on every projected column, for example MIN(i.uuid) AS fsliId and MAX(lm.uuid) AS levelMappingUuid, read through a typed interface projection with one getter per alias, so there is no map to collide. The lesson: in finance code, bugs that raise no error are the dangerous ones, so you need explicit naming plus invariants like "parent equals sum of children".

List<String> labels = List.of("uuid", "level_1", "uuid");   // fact uuid, then mapping uuid
Object[] values = {"fact-123", "Assets", "map-999"};
Map<String, Object> row = new HashMap<>();
for (int i = 0; i < labels.size(); i++) row.put(labels.get(i), values[i]);
// {uuid=map-999, level_1=Assets}   fact identity lost, no exception thrown

The fixed shape:

public interface ComponentScopingRow {
    String getFsliId();             // fact identity
    String getLevelMappingUuid();   // mapping identity, separately named
}

@Query("""
    SELECT MIN(i.uuid) AS fsliId, MAX(lm.uuid) AS levelMappingUuid
    FROM BalanceSheet i JOIN LevelMapping lm
      ON i.levelId = lm.uuid AND i.fiscalQuarter = lm.fiscalQuarter AND i.fiscalYear = lm.fiscalYear
    WHERE i.fiscalQuarter = :q AND i.fiscalYear = :y
    GROUP BY lm.level1
    """)
List<ComponentScopingRow> findComponentScopingRows(@Param("q") String q, @Param("y") String y);

A8. FRM mock interview (10 questions)

Q1. Prove "36 endpoints" isn't padding. The scoping @RestController has 32 request-mapping methods, one of which is /health, so about 31 functional scoping routes. The collaboration-service comment and notification APIs from the design doc bring the FRM backend surface to 36. None are duplicate verbs for padding: the PATCH and PUT routes carry distinct logic like status transitions and benchmark recomputation.

Q2. Why MySQL and not Postgres? SOADB is Uber's MySQL standard for service-owned data, and InnoDB gives the ACID multi-user edits the close needs. Per quarter the working set is tens of thousands of rows, so it's a correctness problem, not a scale problem. I don't need recursive SQL because the ETL flattens the hierarchy into a stable level_id.

Q3. Walk the materiality rule in code terms. Quantitative is YES if the HFM amount is above the materiality metric. Qualitative is YES from the manager's assessment. Overall is Significant if either is YES. A component is financially significant if revenue share is over the benchmark or absolute assets share is over it, 5% by default and configurable through PUT /update_benchmark_thresholds.

Q4. Explain residual risk. Residual balance is HFM amount minus total in scope, and residual multiple is that divided by materiality. It flags leftovers that are still audit-relevant, for example over 50% of materiality. It's served by GET /residual_risk with fsli_type set to bs or is.

Q5. Tell me the column-aliasing bug precisely. A native SQL join projected two columns named uuid, and copying the row into a map by column label kept the mapping uuid, so a PATCH hit the wrong line. I fixed it with explicitly aliased columns, fsliId versus levelMappingUuid, read through a typed projection. Then I led the Spring Data JPA / Hibernate migration so the whole read layer uses aliased, typed queries, not just that one query.

Q6. How do you stop two managers clobbering each other? Optimistic row-locking with a JPA @Version field: the update only applies if the row still has the version the editor read. Otherwise zero rows change, Hibernate throws OptimisticLockException, and the API returns 409 so they reload. Writes are @Transactional service methods keyed by uuid, and multi-table syncs are atomic. Every write records updated_by. The real-time push to other screens was the collaboration service, which I didn't build.

Q7. How would you scale it? It barely needs it. Connections already come from one shared HikariCP pool with connection validation, so dropped MySQL connections are discarded before use. I'd add read replicas (@Transactional(readOnly = true) reads routed to a replica), a per-period GET cache because closed periods are immutable, and indexes on (fiscal_quarter, fiscal_year, level_id). There's no Redis, response cache or Hibernate second-level cache in the shipped service, and I won't invent one.

Q8. Auth is one header. Secure enough? The gateway authenticates the user and injects x-auth-params-email. The service returns 401 if it's missing and records the email on every write. Authorization was enforced upstream. Standalone, I'd verify a signed token with Spring Security and add role checks with @PreAuthorize.

Q9. Did you build the HFM ETL? No. The service consumes HFM-loaded tables, and the pipeline was a shared responsibility. I owned the scoping backend, the schema, the recon v2 migration, and led the ORM migration.

Q10. Is this just a spreadsheet with APIs? Not on risk. The hard part is tree correctness, parent equals sum of children, running v1 and v2 in parallel, and identity bugs under a close deadline. A wrong number becomes PwC audit evidence. That's also why the SOX controls, allowlisted reporting SQL and FSM gates matter.

Part B: Uber Menu Ingestion and Automation (Uber Eats), plus ANZ

B1. The 30-second and 2-minute versions

30 seconds. "At Uber Eats, via EPAM, I built the menu ingestion pipeline. It took restaurant onboarding from 24 hours to 2 hours, saves $600K a year, and processes 30K+ menus a month. Unstructured, multilingual PDF menus are converted into the strict catalog schema at 98% field fidelity in offline evaluation, using Gemini 2.5 Pro with LangChain RAG over Milvus embeddings. I also raised extraction success to 95%+ by hardening a Selenium fleet with dynamic proxy pools and adaptive retries, and designed a Kafka and Apache Flink pipeline with stateful keyed deduplication and schema normalization for exactly-once catalog upserts."

2 minutes. "Restaurant partners send menus as JavaScript-heavy websites, PDFs and images, often in several languages. Acquisition is a Python Selenium fleet on GCP. Anti-bot defences used to kill a lot of runs, so I added dynamic proxy pools and adaptive retries, and success went from an estimated 60 to 65% to 95%+.

Everything lands on Kafka. Flink consumes it, keyed by vendor and menu. It normalizes to the catalog schema, deduplicates using a content hash held in keyed state, and routes unstructured payloads to the AI path. That path uses LangChain to retrieve similar, already-labelled menus from Milvus as context, Gemini 2.5 Pro generates structured output, and a hard schema validation gate checks it before anything is written. Low-confidence results go to human review. On an offline labelled set, field fidelity is 98%.

The catalog write is an idempotent upsert, so in practice 'exactly-once' means at-least-once delivery with idempotent writes: replays never create duplicates. The business result is onboarding from 24 hours to 2 hours, 30K+ menus a month, and $600K a year saved versus a roughly $2-per-menu third-party cost. Separately, under Uber Mobility, I automated driver and vehicle document checks for ANZ to 99.9% compliance, removing 20 hours a week of manual review."

B2. Words you need

Term Plain meaning
Selenium A tool that drives a real web browser from code. Needed because many menu sites only show items after JavaScript runs.
Proxy pool A rotating set of outbound IP addresses. Like sending letters from many post offices so one site doesn't block you.
Adaptive retries Retrying with growing waits and per-site budgets, so one hostile site doesn't burn the whole fleet.
Kafka A durable, replayable log of events. Producers append, consumers read at their own pace. Like a conveyor belt that also records everything that passed.
Apache Flink A stream processor that keeps state per key and checkpoints it, so it can resume after a crash without losing its place.
Keyed state Memory Flink keeps per key (for example per vendor and menu), such as "the last content hash I saw".
Exactly-once vs at-least-once At-least-once means a message may be processed twice after a retry. Exactly-once means the effect happens once. In practice you get it with at-least-once delivery plus idempotent writes.
Idempotent upsert "Insert or update" keyed so that doing it twice gives the same result as doing it once.
Embedding A list of numbers that captures meaning, so similar menus have nearby vectors.
Milvus A vector database that finds the nearest embeddings quickly.
RAG Retrieval-Augmented Generation. Fetch relevant examples first, then give them to the LLM as context. Like an open-book exam.
LangChain A Python framework for wiring retrieval, prompts and LLM calls into a pipeline.
Gemini 2.5 Pro Google's LLM, used here to turn messy menu text into structured fields.
Field fidelity The share of extracted fields that match a human-labelled ground truth.
Offline evaluation Measured on a fixed labelled test set, not continuously on live traffic.

B3. Architecture

flowchart LR SITES["Partner sites and PDFs"] --> SEL["Selenium fleet on GCP with proxy pools and adaptive retries"] SEL --> K["Kafka topics keyed by vendor"] K --> F["Flink: normalize, keyed dedupe by content hash"] F -->|"structured"| CAT["Idempotent catalog upsert"] F -->|"unstructured"| RAG["LangChain RAG"] RAG --> MV[("Milvus embeddings of labelled menus")] MV --> RAG RAG --> GEM["Gemini 2.5 Pro"] GEM --> GATE["Schema validation gate"] GATE -->|"valid"| CAT GATE -->|"low confidence"| HR["Human review"] CAT --> ONB["Uber Eats onboarding, 24 hours to 2 hours"]

What to notice: Kafka decouples scraping from processing, Flink does dedupe before anything is written, and nothing reaches the catalog without passing the schema gate.

Walkthrough.

  1. Selenium fleet on GCP loads each partner's site or file like a real user would, behind rotating proxies, with per-site retry budgets.
  2. Kafka receives raw payloads keyed by vendor. Scrapers never block on slow catalog writes, and a bad parser deploy can be fixed by replaying from an earlier offset.
  3. Flink consumes by key. It normalizes fields to the catalog schema, compares the content hash with what it saw last for that vendor and menu, drops unchanged duplicates, and routes structured items straight to the catalog and unstructured ones to the AI path.
  4. RAG path. LangChain embeds the menu, retrieves similar labelled menus from Milvus, and gives them to Gemini 2.5 Pro as examples. Gemini returns structured fields.
  5. Schema gate. Strict validation. Valid output is upserted. Low-confidence output goes to human review.
  6. Catalog upsert is idempotent by vendor, menu and version or content hash.

Separate track (not on the menu path): ANZ driver and vehicle documents go through a deterministic validation backend for 99.9% compliance.

B4. One menu, step by step

What to notice: a replay after a crash produces the same key and the same content, so the catalog does not get a second copy.

Input (French PDF text):  "Croque Monsieur ...... 9,50 €   (jambon, fromage)"

  "vendor_id": "4411",
  "menu_id": "dinner",

  ]
}

Illustrative keyed dedupe in Flink-style pseudo-code (teaching shape, not a paste of the repo):

class DedupeByContent(KeyedProcessFunction):          # keyed by (vendor_id, menu_id)
    def open(self, ctx):
        self.last_hash = ctx.get_state(ValueStateDescriptor("last_hash", Types.STRING()))

    def process_element(self, menu, ctx):
        h = sha256(canonical_json(menu)).hexdigest()
        if self.last_hash.value() == h:
            return                                    # unchanged menu, drop it
        self.last_hash.update(h)
        yield menu                                    # downstream upsert is idempotent anyway

Acquire Selenium on GCP JavaScript-rendered sites need a real browser Fragile when site layouts change, needs monitoring

Q1. Why Selenium and not a simple HTTP client? Partner menus are rendered by JavaScript, so a static fetch misses items and prices. Browser automation is the acquisition layer. The cost is maintenance when site layouts change, which is why scrape-health checks and the schema gate matter.

Q2. Derive the $600K. We replaced a roughly $2-per-menu third-party cost. $2 times 30K menus a month times 12 is about $720K list, and the resume uses $600K a year as a conservative floor. It's arithmetic on historical ops numbers, and I say that if asked.

Q3. Is 98% live or offline? Offline. It's field fidelity against a labelled evaluation set, and the schema gate validates every record before it's written. I don't present it as a live production SLA. Follow-up they may ask: "How would you monitor it live?" "Sample production outputs into a review queue and track the human-correction rate as an online proxy."

Q4. How does RAG help Gemini here? For each menu, LangChain retrieves similar already-labelled menus from Milvus and passes them as examples. That keeps Gemini's output on our schema and familiar with cuisine and layout patterns, even across languages. The hard schema gate then catches anything that still drifts.

Q5. Did you fine-tune the model? Fine-tuning is not on my resume, so I don't claim it. The resume pipeline is retrieval plus Gemini 2.5 Pro plus a schema gate. Conceptually, supervised fine-tuning would teach consistent field layout and enum adherence so fewer invalid structures hit the gate, and it's a lever I'd consider if gate rejections stayed high.

Q6. What fails without proxies? IP bans, CAPTCHA walls and soft 403s, and success collapses. Rotating IPs, refreshing pools on ban signals and adaptive backoff with per-site budgets brought it back to 95%+. One hostile site can't burn the whole fleet's retry budget.

Q7. What does "exactly-once catalog upserts" really mean? In practice it's at-least-once delivery plus idempotent writes. Kafka and Flink checkpoints mean that after a crash Flink restores its state and rewinds offsets, so some events are processed again. The catalog upsert is keyed by vendor, menu and content hash, so the replay is a no-op. I don't claim zero message loss or two-phase commit across third-party sites.

Q8. Why Kafka and Flink at 30K menus a month? Isn't that overkill? Volume is modest on average, but scrapes are bursty, and the real value is decoupling and replay. Kafka lets scrapers finish without waiting on catalog writes and lets us replay after a bad parser deploy. Flink gives per-vendor keyed state for deduplication and checkpointed recovery. Kafka Streams could also work at this rate, and I'd say so.

Q9. Where's Spark? Not on the resume. Spark is a verbal option for large historical backfills, which are batch-shaped, but the pipeline on the resume is Selenium, Kafka, Flink and the RAG path. Masters India's Kafka is a different product, the GST e-invoicing pipeline, so I keep the two stories separate.

Q10. What's the biggest silent failure mode? A site layout change or CAPTCHA shift that returns empty or partial menus that still look successful. Defences are scrape-health checks, the schema gate, and human review on low confidence. Plus Kafka replay to reprocess once the parser is fixed. I don't claim we never failed.
