1.1 The business in plain English

In India, B2B invoices above a threshold must be registered with a government system, the IRP (Invoice Registration Portal), before they are legally valid. The IRP returns an IRN (Invoice Reference Number) and a digitally signed QR code. Masters India sits between enterprises and the IRP. Clients' ERP systems push invoices to us, singly or in big bulk files. We validate, register, return the IRN and QR, and keep reconciliation and audit trails. Correctness matters more than raw speed, but filing-deadline days bring huge spikes, and a timeout on deadline day loses clients.

1.2 Words you need (short version)

The deep dive has the full glossary. These are the ones you must be able to define on the spot.

  • Strangler pattern: replace a legacy system route by route behind the same front door. Like a strangler fig growing around an old tree until it stands alone.
  • Canary release: send a small percentage of traffic to the new version, watch it, then ramp. The canary in the coal mine.
  • Spring Boot: a Java framework with an embedded web server and sensible defaults, so a service starts from one main method. Spring creates your objects (beans) and injects them where needed. A pre-fitted kitchen module.
  • Thread-per-request: in Spring MVC each request holds one server thread, so a thread waiting on the government portal serves no one else. That is why IRP calls moved to Kafka consumers. A cashier stuck on the phone.
  • Non-blocking client (WebClient): sends an HTTP call and frees the thread while waiting, with timeouts and jittered retries built in. Making toast while the kettle boils.
  • Spring Kafka: @KafkaListener methods consume a topic, KafkaTemplate publishes. DefaultErrorHandler with ExponentialBackOff retries a failed message a bounded number of times, then DeadLetterPublishingRecoverer sends it to the DLQ topic. Three delivery attempts, then the depot shelf.
  • Spring Batch: chunked jobs that read N rows, process, write, commit, and record progress, so a crashed import restarts at the last committed chunk. Moving the bookmark after every chapter.
  • p95 latency: 95% of requests are faster than this. When 95 of 100 buses have arrived.
  • Kafka partition key: same key, same partition, same order. Same surname, same post-office counter.
  • Sharding by tax quarter: separate tables per quarter, the app routes by invoice date. A filing cabinet per quarter.
  • Idempotency key: a unique key per operation so repeats have no extra effect. A raffle ticket can only win once.
  • Exactly-once (in practice): at-least-once delivery plus idempotent writes. The courier rings twice, you sign once.
  • DLQ (dead-letter queue): where repeatedly failing messages park for later replay. The "problem parcels" shelf.
  • Cache-aside: check the cache, on a miss read the database and cache it with an expiry. In Spring Data Redis the stampede lock is setIfAbsent(key, value, ttl), which is Redis SET NX EX. Check your sticky note before walking to the filing room.
  • Distributed tracing and request ID: one ID follows a request through every service. A servlet filter puts it into the logging MDC (a per-thread map that every log line includes), and a Kafka header carries it to consumers. A parcel tracking number.

1.4 Architecture

flowchart LR ERP["Client ERP or dashboard"] --> GW["Nginx gateway: canary percent"] GW --> API["Spring Boot: auth, submit, bulk import, recon"] GW -.->|"fallback"| PHP["Legacy PHP"] API --> RD["Redis: config, GSTIN, tokens"] API --> PG["PostgreSQL by tax quarter"] API --> K["Kafka: chunks, IRP jobs, webhooks, audit"] K --> W["Kafka consumers and Spring Batch jobs"] W -->|"bounded concurrency"| IRP["Government IRP"] W --> MG["MongoDB: payload and response snapshots"] W --> DLQ["Dead-letter queue"] API --> OBS["ELK and New Relic"]

What to notice: request threads never call the IRP directly. Workers do, with bounded concurrency, idempotency keys and a DLQ.

Walkthrough. The gateway sends each route to PHP or Spring Boot by percentage, so rollback is a config change. The Spring Boot service validates the request with Bean Validation (@Valid on the DTO), uses Redis for hot lookups, and writes accepted invoices to the current quarter's PostgreSQL shard through a HikariCP pool. Background work goes onto Kafka through KafkaTemplate, keyed by GSTIN. Kafka consumers and Spring Batch jobs do the work: consumers call the IRP through WebClient with a timeout and backoff, store raw responses in MongoDB, update PostgreSQL and fire webhooks. PDFs and email run as @Async or scheduled jobs. Failing batches park in the DLQ. Every log line carries a request ID into ELK, and New Relic traces the path. Migration rule: shared database until a route is 100% on Spring Boot, then carve out service-owned tables.

Illustrative Spring Kafka retry and DLQ setup (teaching sketch, values not from production):

@Bean
DefaultErrorHandler kafkaErrorHandler(KafkaTemplate<String, Object> template) {
    var recoverer = new DeadLetterPublishingRecoverer(template);   // -> <topic>.DLT
    var backOff = new ExponentialBackOffWithMaxRetries(4);         // bounded retries
    backOff.setInitialInterval(500);
    backOff.setMultiplier(2.0);
    backOff.setMaxInterval(30_000);
    var handler = new DefaultErrorHandler(recoverer, backOff);
    handler.addNotRetryableExceptions(InvalidInvoiceException.class); // bad data skips retries
    return handler;
}

What to notice: retries are capped, waits grow each time, and a malformed batch goes straight to the dead-letter topic so the rest of the import keeps moving.

1.5 One bulk import, step by step (illustrative)

  1. A client uploads a 100,000-invoice file. We store it in S3 and compute its file hash.
  2. A Spring Batch step reads it in chunks (say 1,000 rows, illustrative), indexes 0 to 99, and publishes chunk events to Kafka keyed by the client's GSTIN. If the step dies mid-file, a restart resumes at the last committed chunk.
  3. A @KafkaListener consumer takes batch 37 and tries to claim key client + fileHash + 37 with a unique-constraint insert. It succeeds, so it calls the IRP with bounded concurrency.
  4. The IRP returns IRNs and signed QRs. The worker stores raw responses in MongoDB, marks rows registered in the quarter shard, and pushes a progress update.
  5. If the worker crashes before acknowledging, Kafka redelivers batch 37. The claim already exists, so the IRP call is skipped. No double registration.
  6. If batch 37 keeps failing (a malformed row), Spring Kafka's error handler sends it to the DLQ after the retry budget. Batches 38 to 99 continue. An operator fixes and replays it later.

1.8 Mock interview: 10 questions

Q1. Why Kafka over SQS or RabbitMQ for e-invoicing? "We needed per-client ordering, durable replay for GST disputes, and independent consumer groups on one log, so we partitioned by GSTIN. SQS loses cheap multi-consumer replay once a message is acked, and FIFO caps throughput per group. RabbitMQ could honestly have dispatched work at our scale. Replay, multi-reader audit, and Spring Kafka's built-in listeners, bounded retries and dead-letter publishing are why Kafka won."

Q2. Derive TPS and RPS. Do the numbers hang together? "A million a day is about 11.6, so roughly 12 a second on average, and I'd size peaks at 8 to 10 times that, so 100-plus. Those are estimates. 700 to 4,000 requests a minute is about 12 to 67 a second. Requests per minute is gateway and service capacity, daily submissions are registered documents, so they're complementary meters. I keep TPS and RPS off the resume."

Q3. Caching can't take p95 from 1.2 seconds to 300 milliseconds. What did? "The tail came from PHP workers held hostage by IRP calls. In Spring Boot, request threads stopped waiting on the IRP: they publish to Kafka and return 202, and consumers call the portal through WebClient with timeouts. HikariCP pooling, N+1 removal in Hibernate and composite indexes did the rest. Redis cut redundant reads by about 30%, which helped the median, not the tail."

Q4. Cache-aside: keys, TTL, invalidation, herd? "Miss, read the DB, set with a TTL. Hot keys were IRP auth tokens with a TTL under the token life, client config and flags, GSTIN masters and tax rates. Config and GSTIN were deleted on write. Masters used TTL with jitter. For the herd, a setIfAbsent lock in Spring Data Redis, which is Redis SET NX with an expiry, so one worker rebuilds and the others wait or serve slightly stale. The 30% is plausible because 100K-row imports repeat the same lookups."

Q5. Why shard by financial quarter? "GST returns and filing spikes are quarter-scoped. Writes land in the current quarter, older quarters are reconciliation and audit reads. Quarter tables mean smaller hot indexes and clean archiving. The cost is app-level routing and the risk is a wrong-quarter write, so we derived the quarter from the invoice date at the API boundary and rejected mismatches."

Q6. Sketch the IRP path and where Kafka sits. "The client posts JSON, we validate schema and GSTIN, register with the IRP, and get a signed IRN and QR. Kafka carries accepted chunks, IRP submit jobs, response snapshots to Mongo, and client webhooks. Idempotency stops double registration. Bulk files go through S3 and a Spring Batch chunking step, then Kafka consumers send them to the IRP with bounded concurrency and dashboard progress. That's how we handle 100K-plus imports and a million-plus submissions a day."

Q7. What did "mentored two" mean day to day? "I set the conventions: controller, service, repository layering, Bean Validation DTOs at the boundary, retry and idempotency helpers. Each engineer owned a service extraction. I did heavy PR review early and paired on the first Nginx percentage canary, watching errors and latency to ramp or roll back. The shared database during cutover kept things safe."

Q8. Triage down 70%: vanity or real? "Before, SSH and grep with no correlation. After, a request ID through the API, the Kafka consumer and the IRP worker, New Relic APM, alerts on errors and latency. Roughly 30 minutes to under 10 is my estimated baseline behind the 70%. I claim alerting, not unproven pager ownership. Coverage went from 35% to 82% on money paths, and deploy success reached 98%."

Q9. Dual writes during migration? "Avoided. A shared database through the traffic cutover kept one source of truth. Table ownership split only after 100% of a route was on Spring Boot. MockMvc contract tests pinned PHP response shapes field for field."

Q10. What broke in an early canary? "A timeout mismatch. PHP allowed 60 seconds and we'd set 10. Legitimate long IRP calls failed. We moved IRP calls fully off the request thread onto Kafka consumers and returned 202 with polling. The canary caught it before full ramp."

2.1 The business in plain English

GeeksforGeeks runs coding articles and paid courses. The doubt-support platform is the Q&A layer where learners ask questions on articles and courses and vote on helpful answers. Live coding contests drive about ten times normal traffic. The old PHP backend buckled under those spikes. Words you need: Django is a "batteries included" Python web framework (admin, auth, ORM), like a fully equipped kitchen. Hot row is a single database row updated so often it becomes a bottleneck, like the one checkout lane everyone queues at. Locking a thread means closing it to new replies. Lease lock is a short-lived "room booked" sign so only one host runs a scheduled job.

2.3 Architecture

One vote, step by step. A learner upvotes answer 5521. Django checks the thread isn't locked and the user may vote. It inserts into votes (user_id, content_id) with a unique key, so a double tap is a no-op or update. It increments Redis votes:5521. A periodic job reconciles Redis counts to MySQL.
