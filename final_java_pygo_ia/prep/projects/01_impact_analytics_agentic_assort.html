2. The business in plain English

Who the users are. Merchandise planners at retail companies. A planner decides things like "next autumn we will sell these 400 women's tops in these 120 stores, and we will stop selling these 60." AssortSmart is the SaaS (software as a service) product they do this in. Many retailers share one platform, and each retailer is called a tenant.

What they do in the product. They open large pivot grids of sales, stock, margin, sell-through and rate of sale, sliced by product, store, product attribute and week or season. They define their own KPIs (key performance indicators, the business metrics they track). And every season they decide, product by product, what stays in the range.

What hurt before. 1. Slow screens. Pivots were computed live from raw data on PostgreSQL. On a 250-million-row test, a typical pivot took 189 seconds. 2. Too many decisions to review by hand. A large retailer has hundreds of thousands of article-seasons. Simple rules like "drop if sell-through is below 40%" miss context, for example a product that sells slowly because it launched late or only sells on discount. 3. Every new KPI needed a code release. 4. Strict data separation. Each retailer must see only its own data, and each planner only the part of the product hierarchy they are allowed to see.

Why the company paid for this. Fast screens mean planners actually use the tool in planning season. Good keep and drop decisions reduce unsold stock and markdowns. Explanations make planners trust the AI. Cost and reliability controls make it affordable to run the AI for every client every season.

Words you need

Term Plain meaning
Article-season One product in one selling season. "Blue linen shirt, Summer 2026" is one article-season.
Sell-through / rate of sale Sell-through is the share of stock that sold (80 of 100 units is 80%). Rate of sale is units sold per store per week.
LLM lens One focused question the LLM (large language model) answers about an article, such as "Do other colours of this style steal its sales?" It returns a score, a confidence and reason codes.
Deterministic Same input always gives the same output. Normal code is deterministic. LLM calls are not.
ClickHouse A columnar analytics database. It stores each column separately and compresses it, so summing a column over billions of rows is fast.
Rollup A table of totals computed ahead of time, so screens read totals instead of raw rows. Like a monthly bank summary instead of re-adding every transaction.
ReplacingMergeTree A ClickHouse table type that keeps only the newest version of a row with the same key. Think of a notebook where you never erase: you write the new value below, and a cleaner later crosses out the old lines.
Circuit breaker After too many failures in a row, stop calling a failing service for a while. Like a home fuse that trips to protect the wiring.
Checkpoint Saved progress so a job can resume where it stopped. Like a video game save point.
Google Wire A Go tool that generates the code that wires components together at build time, so a missing dependency fails the build instead of production. This is called compile-time dependency injection (DI).
h2c HTTP/2 over plain TCP without TLS on that hop. HTTP/2 lets many requests share one connection.
UAM User Access Management: which user may see which part of the data.
OOM Out of memory. A query used more RAM than allowed and was killed.
CI gate An automated check in the build pipeline that blocks a change if a score is below a threshold.

3. Architecture

flowchart LR subgraph PLAT["Core platform, Go"] UI["Planner UI"] --> EDGE["Go/Gin API edge<br/>Wire DI, h2c, nested timeouts"] EDGE --> AUTH["Auth waterfall<br/>Redis, Firebase Admin, JWT and Google OIDC"] AUTH --> PG["PostgreSQL<br/>roles, UAM scopes, metadata"] EDGE --> KPI["KPI formula parser"] KPI --> ROLL["ClickHouse rollups<br/>six tables"] RAW["Daily facts"] --> LOAD["Rollup loaders<br/>one fiscal week per insert"] LOAD --> ROLL ROLL --> PUMP["Go native-TLS pump<br/>500k-row batches"] PUMP --> CH2["Target ClickHouse Cloud cluster"] EDGE -.-> DD["Datadog traces"] end subgraph AI["Agent plane, Python"] MASTER["ClickHouse master<br/>2.11B rows"] --> PREP["Feature prep and KPI math<br/>gives s_det"] PREP --> PAY["JSON payloads"] PAY --> REG["Orchestration registry<br/>peer, decider, 7 lenses"] REG --> BLEND["Blend<br/>0.4 s_det plus 0.6 s_agent"] PREP --> BLEND REG -.-> FB["Fallback to s_det on timeout"] FB --> OUT["Decision rows<br/>ReplacingMergeTree, config_hash"] BLEND --> OUT IRIS["Ask Iris copilot<br/>WebSocket, LangGraph supervisor"] -.-> LS["LangSmith traces"] end

What to notice: screens read rollups, never raw facts. The LLM only ever sees JSON, and our code does every database read and write. Every failure path in the AI batch still produces a row.

Walking through it, left to right.

The core platform is the Go side. A planner's browser calls the Go/Gin API edge, a single Go process that handles routing, JSON, auth, timeouts and tracing. There is no reverse proxy (such as Nginx) in front of it, so the edge protects itself with nested timeouts. The auth waterfall answers "who is this?" cheaply: Redis first (a cache of recently verified identities), then the slower verifiers. PostgreSQL answers "what may they see?" through roles and hierarchy scopes. When a screen needs a KPI, the formula parser turns the user's formula into a safe SQL fragment, and the query runs against one of six ClickHouse rollup tables. Separately, on the write side, loaders build those rollups from raw daily facts one fiscal week at a time, and the Go pump copies rollup partitions to another ClickHouse Cloud cluster. Datadog records a trace for every request.

The agent plane is the Python side (FastAPI and LangGraph). Our Python code reads the 2.11-billion-row ClickHouse master, computes KPIs, and produces the deterministic score s_det. It packs only the fields the LLM needs into JSON payloads. The orchestration registry runs the fixed batch order: peer benchmark context, then a decider that picks which lenses matter and how to weight them, then the seven lenses. Their combined score is s_agent. The blend gives the final score, and the result is written as decision rows through ReplacingMergeTree, each stamped with a config_hash. If the LLM times out, the item falls back to s_det and still gets a row. Ask Iris is the chat copilot where planners query KPIs and inspect these decisions, traced in LangSmith.

A tiny worked example of the blend (illustrative numbers, real formula and threshold). A blue linen shirt gets s_det = 0.62 and s_agent = 0.50. The final score is 0.4 × 0.62 + 0.6 × 0.50 = 0.248 + 0.300 = 0.548. The rule is keep if the final score is at least 0.55, so this article is a Drop, with an explanation like "Sell-through is acceptable, but demand is slowing and most units sold on discount." If the LLM had timed out, the shirt would get its deterministic outcome (0.62, so Keep) and the other items in the pass would carry on.

5. Key design decisions (short form)

Each decision has the what, why, alternative and trade-off. The full version is in the handbook chapters.

The LLM never queries the database (A2). What: the model gets JSON prepared by our code. Why: a model writing SQL against 2.11 billion rows could run unbounded scans, break tenant scoping, or invent numbers. Our code computes the math once and the same way every time. Alternative: give the agent a SQL tool. Why not: cost, safety, and tests could no longer check the numbers. Trade-off: the payload must be designed carefully, and the LLM can only reason about what we chose to send. If asked what I'd change, I would keep this boundary.

Deterministic score plus LLM lenses, with fallback (A1, A2). What: money math stays in Python, the LLM only adds qualitative judgement. Why: LLMs are good at weighing evidence and explaining, and bad at arithmetic. Alternative: let the LLM decide alone. Why not: no stable baseline and no safe fallback. Trade-off: two scores to maintain and a blend to justify. The evaluation in A5 is exactly how we kept that honest.

App-native orchestration registry instead of Airflow or Temporal (A3). What: one Python registry shared by all three pipelines. Why: we needed resume logic tied to our own checkpoints, ClickHouse inserts, config hashing and per-run cost JSON. Alternative: Airflow or Temporal, which are strong general workflow engines. Why not: more infrastructure than a batch job with a resume flag needed. Trade-off: we own the retry and resume code ourselves. If the number of pipelines grew a lot, I would revisit a workflow engine.

Rollups, and building them one fiscal week at a time (C4). What: six pre-aggregated tables, loaded week by week. Why: screens read totals instead of raw rows, and one week fits in memory where a whole season did not. Alternative: bigger memory caps. Why not: a whole season failed even at 80 GB and 200 GB caps. Trade-off: many more insert statements to run and track, in exchange for a build that finishes.

A custom Go pump with drop-and-recopy rollback (C5). What: our own native-TLS copier instead of ClickHouse's built-in cross-cluster copy. Why: IP allowlists blocked cluster-to-cluster copy. Trade-off: during a recopy, readers of the target can see a partial season. A swap-based design using REPLACE PARTITION from scratch tables was written but not executed. That is what I would do next.

6. Practice questions

1. "Walk me through the Keep/Drop decision for one product." I start with deterministic math. Python computes sell-through and rate of sale and turns them into a score called s_det. Then up to seven LLM lenses each answer one focused question, like whether other colours are cannibalising the product, and a decider weights them into s_agent. The final score is 0.4 times s_det plus 0.6 times s_agent, and we keep the product if it is at least 0.55. For example, 0.62 and 0.50 blend to 0.548, so that shirt is a drop, with a written reason the planner can read. Follow-up they may ask: "Why 0.4 and 0.6?" Those weights are frozen configuration. When the LLM underperformed the baseline, we froze them rather than retune them to look good.

2. "Why not let the LLM query ClickHouse directly?" Because the master table has 2.11 billion rows, and a model writing SQL can run unbounded scans, ignore tenant scope, or get the math wrong. Our code reads ClickHouse, computes the KPIs once, and sends the model a trimmed JSON payload. That keeps cost bounded, keeps numbers testable, and means the model can only reason about data we chose to give it. The model never gets a SQL tool.

3. "What happens when the LLM provider goes down mid-run?" The run still finishes. Every call has a hard timeout, and if a call times out the item falls back to its deterministic score and is marked as a fallback. If failures keep coming, about five in a row, the circuit breaker trips and stops hammering the provider. Checkpoint files mean that when we restart with --resume, we skip the deterministic scoring and the batches that already completed.

4. "How do you know which settings produced a given decision?" Every output row carries a config_hash. It is a SHA-256 fingerprint of the guardrails, parameters, prompts and catalog used in that run. If a planner questions a decision, I can match it to the exact configuration. We also write JSON telemetry per run with tokens, USD cost, step duration and how many batches fell back.

5. "Your CI gate is 80%. Is the product 80% accurate in production?" No, and I'm careful about that. 80% is the promotion bar on a 300-case evaluation set in CI. A change that scores below it cannot ship. It is a guardrail, not a claim that every tenant sees 80% live. Follow-up they may ask: "Where do 73% and 74% come from?" From a separate 200-case gold benchmark, not the 300-case file.

6. "Tell me about the 73% cost reduction." On a separate 200-case gold benchmark, we compared models and found a cheaper one that completed all 200 cases, so 100% coverage, at 73% lower live execution cost. The same benchmark showed the deterministic baseline at 74%. The blended LLM came in around 63%, below that baseline. So instead of retuning the blend weights until the numbers looked better, we froze them. I'd rather ship an honest system than an overfit one.

7. "How does Ask Iris stop one retailer seeing another's data?" The planner's JWT is verified once when the WebSocket opens, and their hierarchy scope is frozen at that handshake. Later messages in the conversation can't change it. A LangGraph supervisor routes each step, and an evaluator loop retries a weak answer at most three times, so the model can't loop forever. LangSmith gives us a trace of every step. Follow-up they may ask: "What's its latency or usage?" It's a shipped capability. I don't quote usage or SLA numbers.

8. "How did you make pivots 15.5 times faster?" Pivots were adding up raw rows live. I built a pre-aggregation layer in ClickHouse: six rollup tables for product, store and attribute, each by season and by week, partitioned by season. On a 250-million-row test harness, a pivot went from 189 seconds to 12 seconds, 12.3 rounded. That is 15.5 times faster. Follow-up they may ask: "Was the 170 GB crash part of that?" No. That was a separate problem in building the rollups, which is load time, not query time.

9. "Tell me about the 170 GB out-of-memory crash." Building the weekly rollups for a whole season in one INSERT SELECT ran out of memory. It failed even with 80 GB and 200 GB caps. I sliced the build into temporal chunks, one fiscal week per insert, and set explicit memory and disk-spill caps so ClickHouse writes partial results to disk instead of dying. Each statement now handles a slice that fits in memory, so the build completes.

10. "Why write your own data pump instead of using ClickHouse's copy?" The normal cluster-to-cluster copy was blocked by IP allowlists between the ClickHouse Cloud clusters. So I wrote a Go pump that reads from one cluster and writes to the other over ClickHouse's native protocol with TLS. It uses 500,000-row double-buffered batches, reading the next batch while sending the previous one, and reached about 344,000 rows per second combined across two season streams. TSV ledgers and checkpoint files record finished work, and if a season's copy fails we drop that partition and copy it again, so we never keep a half season that looks complete. Follow-up they may ask: "Is that rollback atomic for readers?" No. During a recopy readers can see a partial season. A REPLACE PARTITION swap design was written but not executed.
