## 2.1 Flagship — AI / agentic orchestration

### A1 — Multi-agent decomposition
> **Architected a router→orchestrator→specialist multi-agent system (5 domain agents) that decomposes a natural-language planning question into a validated execution DAG, raising decomposition quality from 0.54 to 0.99 across a 12-query offline eval by adding a structural DAG validator plus a single LLM self-repair pass — removing the No. 1 production failure of LLM planners (malformed plans).**

**Backing.** *Why:* free-form "let the LLM plan" produces invalid or under-specified plans that break downstream execution. *How:* a **Router** LLM classifies intent → `single | orchestrate`; a **Decomposer** emits `{sub_queries[], path[][]}` (an agent-routed DAG); a **`plan_schema.validate()`** gate rejects unknown domains, duplicate ids, over-wide stages, and — critically — **forward references** in `<A_n>` placeholders before anything executes; on failure it re-prompts the LLM once with the validation errors (`repaired=True`). *Tradeoff:* one extra LLM round-trip on the ~small fraction of invalid plans vs. cascading executor failures — cheap insurance. *Decision path:* chose a **prompt + hard validator** over a fine-tuned planner (faster, deterministic, debuggable) and over free-form ReAct (unpredictable). *Impact:* structural correctness 0.54→0.99 **[EVAL, 12 gold queries]**; the validator makes failures explicit and recoverable. *Evidence:* `agentic_assort_multiagent/core/{router,decomposer,plan_schema,orchestrator}.py`; `docs/03`. *Honesty:* the score is an **offline structural eval** on mock model outputs — say "in an offline evaluation harness."

### A2 — Parallelism + dependency passing + caching
> **Cut agent-pipeline latency by executing independent sub-queries in parallel within each DAG stage (thread pool) and passing cross-agent results through `<A_n>` placeholder rephrasing, and eliminated repeat work with a pgvector semantic cache (cosine similarity + TTL) that short-circuits the whole pipeline on similar questions.**

**Backing.** *Why:* a planning question fans out to several agents; running them serially is needlessly slow, and users re-ask near-identical questions. *How:* the orchestrator walks `plan.path` **stage-by-stage (sequential)** but runs agents **within a stage concurrently** via `ThreadPoolExecutor(max_workers=max_per_stage)`; when a later stage depends on an earlier answer, a **rephraser** substitutes `<A1>` with the prior result before dispatch; a **`SemanticCache`** embeds the query and returns a cached answer when cosine-similarity ≥ threshold and TTL is fresh (pgvector `<=>` in prod, in-memory offline). *Tradeoff:* thread pool (not asyncio) because the agent I/O is largely blocking DB/LLM SDK calls — simpler and correct for the workload; cache adds a staleness window bounded by TTL. *Impact:* removes serialization on the fan-out and avoids full-pipeline recompute on repeats. *Evidence:* `core/orchestrator.py`, `connectors/cache.py`. *Honesty:* design/architecture property; no production latency number attached.

### A3 — Resilient agents + safe text-to-SQL
> **Built self-contained specialist agents on a `validate→fetch→analyze→narrate` lifecycle with exponential-backoff retries and partial-failure synthesis (the orchestrator still returns a useful answer when one agent errors), and generated text-to-SQL with hard guardrails — SELECT-only, `LIMIT` caps, `NULLIF` denominators, no `SELECT *`.**

**Backing.** *Why:* one flaky data call shouldn't fail the whole answer, and LLM-authored SQL is a foot-gun (runaway scans, division-by-zero, full-table reads). *How:* `BaseAgent.answer()` never raises — a failure returns `AgentResult(status="error")` so `_synthesize()` produces a **PARTIAL** answer; `with_retries()` wraps transient `fetch()` with 0.2/0.4/0.8s backoff; the text-to-SQL prompt is constrained and the result is validated before execution. *Tradeoff:* partial answers must be clearly labeled to the user (trust) — surfaced via status + reason. *Impact:* graceful degradation instead of hard failure; bounded, safe queries. *Evidence:* `agents/base.py`, `core/retry.py`. *Honesty:* implemented in the PoC; production hardening (timeouts, circuit-breakers) is the next step — good thing to volunteer.

### A4 — Governed autonomy (human-in-the-loop)
> **Designed the agent autonomy model — agents act unattended only within confidence/impact thresholds; above threshold they raise a human-in-the-loop "Signal" with a reason code, and every agent action and human decision is written to an immutable audit log — enabling safe overnight automation.**

**Backing.** *Why:* merchants won't trust an agent that silently changes a multi-million-dollar buy; autonomy must be bounded and auditable. *How:* `isAutonomous`/`aboveThreshold` gate actions; the **Signals** worklist carries Accept/Skip/Edit/Dismiss + reason; the **Log/audit trail** records who/what/when; overnight actions produce a morning summary. *Tradeoff:* thresholds too tight → agents feel useless; too loose → risk. Chose explicit, per-signal confirmation above threshold + full audit as the trust anchor. *Impact:* makes "overnight autonomy" acceptable to the business. *Evidence:* `product_artifacts/…Knowledge.md` (Signals/Log/autonomy threshold). *Honesty:* product-design + prototype behavior; frame as "designed the governance model."

## 2.2 Flagship — Agentic Cluster Recommendation Copilot (the module now in build)

*This is the concrete, shipping instantiation of the agentic vision: a dedicated agent for the store-clustering module, spec'd in the Agentic Cluster FRD v1.8 (companion HLD/LLD) with measured baselines from live tenant audits. These bullets are the freshest and most defensible "senior owns a system end-to-end" material — lead with 1–2 of them.*

### C1 — The copilot itself (own the system story)
> **Designed an agentic store-clustering copilot — deterministic tools compute on a dedicated ClickHouse read plane, an LLM orchestrates and explains, and three human confirm-gates govern every write — targeting hierarchy-to-finalized-plan under 1 hour (from days), ≥20 configurations explored per plan (from exactly 1), and run failures below 2% (from a measured 8.5%) with 100% reproducible shipped clusterings (from 0%).**

**Backing.** *Why:* clustering is the foundation of every assortment strategy plan yet the least assisted step — the system already computes attribute significance, then makes the human choose from raw score lists; users try **1 configuration per plan** in a search space of 12 algorithms × k 3–10 × any attribute subset; **8.5% of runs fail (37/437 on the kik tenant, >80% on input mistakes)** and nothing is reproducible (algorithm/params/seed never persisted) **[FRD-measured]**. *How:* invert the workflow — the user states **intent** (hierarchy + reference period, the only two non-derivable inputs); the agent handles scoping (active stores, sister-store substitution, sample-size guards), attribute selection (significance + coverage + redundancy gates → ranked feature sets), and batch exploration (20–100 pruned configs against an isolated scratch plan, results streaming as they score); the human confirms at **3 gates** and injects business knowledge (pins/moves). Approved results **write back into the existing product tables unchanged** — strategy/budget/wedge/line consume them with zero product changes. *Key design position:* the LLM never computes — **deterministic tools compute, the LLM orchestrates and explains**; same inputs + same scorer version ⇒ identical ranking. *Tradeoff:* an agentic layer beside (not replacing) the manual wizard doubles surfaces, but de-risks adoption — both modes converge on the same config document, gates and write-back (the "convergence rule"). *Impact targets (6-mo):* <1 h to finalized plan, ≥20 configs, <2% failures, ≥60% top-3 acceptance **[FRD-target]**. *Evidence:* Agentic Cluster FRD v1.8 §§0–2, 5, 6. *Honesty:* baselines are measured from live tenants; targets are committed design goals — say "measured baseline / design target."

### C2 — The ClickHouse read plane (data-infra story)
> **Cut agent data-probe latency from 1–20s+ (shared BigQuery slots, uncontrolled variance) to a p95 < 500 ms deterministic target by standing up a dedicated ClickHouse read plane fed by the existing BQ→ClickHouse ingestion lane — with agent access enforced read-only at the database-profile level, nightly precompute converting ≥80% of sessions from cold to warm, and cube-to-BigQuery reconciliation within 0.1%.**

**Backing.** *Why:* an interactive copilot dies on 1–20s data probes; BigQuery's shared-reservation variance is the killer, and ad-hoc agent load on the shared slots hurts everyone else. *How:* reuse the org's proven BQ→ClickHouse ingestion pipeline (built for ItemSmart) to feed a **dedicated instance**; precompute significance + top candidates nightly for hierarchies with active plans; quote data-as-of in every recommendation; per-partition reconciliation guards derived-data rot. *Decision path:* this is the gated forward option from my reconciled DB verdict (L1) actually exercised — ClickHouse only for the read/pivot plane, BigQuery stays truth, Postgres stays the editable SoR; the FRD's non-goals state it explicitly ("NOT moving transactional data to ClickHouse"). *Tradeoff:* a derived copy that can rot (the org base rate is real) — mitigated by owned ingestion + freshness sentinel; and accepted physics on the ML itself (~9 s/config median model fit — we parallelize around it, we don't pretend to speed it up). *Impact:* P0 exit gate is p95 < 500 ms and 0.1% reconciliation **[FRD-target]**; compute baselines measured over 370 live runs (median job ≈20 s, max 463 s) **[FRD-measured]**. *Evidence:* FRD §§0, 3, 6–8; US-09/US-10.

### C3 — Deterministic grounding (the anti-hallucination story)
> **Made chat-native intent safe by grounding every free-text mention deterministically — department names backtracked to full hierarchy paths via catalog search (never LLM guesses), season labels resolved against the tenant's fiscal calendar, ambiguity surfacing a clarifying question — with a confirm-required grounding card, so one prompt like "cluster Pet, Electrical and Cookware for Summer 2025" safely fans out to N parallel pipelines.**

**Backing.** *Why:* the #1 way agent products lose trust is silently acting on a misparsed scope; hierarchy labels are ambiguous across levels and seasons differ per tenant and hemisphere. *How:* mentions → deterministic catalog backtracking to full paths (multiple departments → multiple filters); "Summer 2025" → fiscal-calendar + season-registry resolution with resolved dates displayed; the **grounding card** (scope, store cohort, sister-store substitutions, proposed attributes, each with a reason) must be confirmed before anything executes; batch intents get one disambiguation — *together or separately?* — then run as parallel pipelines bounded by a tenant concurrency budget. *Tradeoff:* an extra confirmation step per session vs. silent wrong-scope compute — cheap, and it doubles as the evidence surface. *Impact:* eliminates the input-error class behind >80% of today's run failures **[FRD-measured]**; acceptance criteria US-12/US-15. *Evidence:* FRD §2.1, US-12, US-15. *Interview gold:* "the LLM arranges the conversation; a catalog search decides what the words mean."

### C4 — Reproducibility, pins & governed autonomy (the trust story)
> **Turned clustering from unreproducible one-shots into auditable, re-runnable artifacts — every shipped clustering persists a content-addressed config document (algorithm, k, params, seed, features, windows, pins, data watermark, scorer version), planner store-moves become durable "pin" constraints honored by every future re-run (0% → 100% survival), and autonomy is a three-level delegation ladder (copilot → autopilot-with-approval → standing drift monitor) where no path ever auto-finalizes.**

**Backing.** *Why:* today the winning configuration is thrown away (0% reproducible), and a planner's manual store swap is silently erased by the next re-run — human knowledge has no durable home **[FRD-measured]**. *How:* the **config document** is the unit of record — persisted, content-addressed, re-runnable ("re-run reproduces membership on the same watermark or explains drift"); **pins** persist as constraints with required reason codes and survive every refresh; delegation levels: L1 copilot proposes/executes on confirmation → L2 autopilot runs one intent end-to-end for a single review → L3 nightly drift monitor raises re-clustering proposals — and **system-originated work never self-finalizes** (surfaces as *pending intents* unless the tenant grants recorded standing pre-approval). A flow audit of 19 workflows produced a **closed-loop terminal-states contract** (every flow defines success / rejection / failure / expiry — nothing accumulates silently). Deviations from recommendations are captured with reasons and feed three honest learning loops: deterministic memory → human-approved calibration → labeled corpus for a future ranker (no silent self-tuning). *Tradeoff:* gates add friction vs. pure autopilot — chosen deliberately; `is_final` is a human signature. *Evidence:* FRD §§2.2–2.5, US-05/08/16/17, OD-1–OD-6. *Honesty:* this is design-you-own + spec'd acceptance criteria; implementation is phased P0–P3.

### C5 — The strategy doorway (cross-module product thinking)
> **Closed the product's most-consumed dead-end — strategy plans must bind to a cluster plan at creation with zero help choosing (live audit: 1 in 5 finalized cluster plans had zero stores attached; briscoes' inventory 100% >17 months stale) — by shipping a deterministic ≤2s FitScore ranking with hard eligibility gates, per-candidate explain cards ("explains X% of store-revenue variance"), and an inline spawn path that runs the full recommendation pipeline inside strategy-create, backtested against 467 historical bindings.**

**Backing.** *Why:* every strategy plan binds to exactly one cluster plan; the audit even found strategies pointing at cluster plans that no longer exist — a silent-breakage class. *How:* hard eligibility gate first (finalized ∧ not deleted ∧ non-empty membership ∧ recoverable scope — never score the unusable); **FitScore** ranks in ≤2 s (cheap terms for all candidates, the variance-explained term only for the top-5, computed on the last comparable season, penalized for cluster count, weighted by store coverage); bands (Green/Yellow/Red) **calibrated by backtesting against 363 kik + 104 briscoes historical bindings**; always a top-3 shortlist (padded with a spawn card — never an empty dropdown); spawn writes at the pre-finalize step and promotes only on human confirmation, or parks as a pending intent under tenant governance; every spawned plan records `created_via` + full scope keys so future doorways match it; and the create API now **validates bindings are live and finalized** — eliminating the dangling-reference class. *Impact target:* ≥40% of new strategy plans created with a suggested cluster plan **[FRD-target]**. *Evidence:* FRD §2.2, US-07. *Interview gold:* the eligibility-gate stat — "1 in 5 finalized plans would silently break every downstream step; we made them unrankable."

## 2.3 Flagship — Data / database architecture

### D1 — Three-tier data spine
> **Designed the platform's three-tier data spine — BigQuery (source of truth + batch cube builds) → Postgres (editable, ACID system-of-record) → ClickHouse/DuckDB (OLAP pivot & hindsight serving) — deliberately separating transactional grid edits from scan-heavy analytics instead of forcing one engine to do both.**

**Backing.** *Why:* the product is "two shapes in one" — **OLTP-with-pivot** (an editable pivoted grid needing ACID + read-after-write) and **OLAP** (scan-and-aggregate hindsight). No single engine is best at both. *How:* BigQuery holds raw facts + builds the pre-aggregated planning cube via scheduled ELT; Postgres owns the editable plan (ACID, stored procs); DuckDB hydrates a plan slice for in-process pivots; ClickHouse is the gated read/pivot serving layer at scale. *Tradeoff:* more moving parts + a sync path vs. one-DB simplicity — justified because "everything in one OLAP DB" breaks transactional writes and per-edit cost, and "everything in BigQuery" hits DML quota/latency walls for interactive edits. *Decision path:* scored 4 engines across capabilities (writes, pivot latency, huge scans, cost) — Postgres wins writes, ClickHouse/DuckDB win pivots/scans — then assigned each its best job. *Impact:* each workload runs on the right engine; BigQuery stays truth in every scenario. *Evidence:* `docs/05` §7 scorecard; `db_architecture_poc/`. 

### D2 — Insert-only / versioned ClickHouse (the key insight)
> **Unlocked ClickHouse as a planning store by designing an insert-only/versioned write model — `ReplacingMergeTree(version)` + `argMax(version)` reads, soft-delete, and atomic `REPLACE PARTITION` for bulk re-seeds — that holds the async mutation queue at zero, sidestepping ClickHouse's ~1,000-mutation ceiling while natively powering overrides, version-diff and undo/redo.**

**Backing.** *Why:* ClickHouse is superb at OLAP pivots but its `ALTER UPDATE/DELETE` **mutations are async and degrade past ~500 / stop past ~1,000** — and a planning grid is edit-heavy, which is exactly why the *legacy* audit said "no ClickHouse." *Insight:* that objection is a property of the *legacy in-place-UPDATE* code, **not** of planning itself. The new grid is built around versions/variance/undo, so an edit can be an **INSERT of a new version** instead of an UPDATE. *How:* every cell edit inserts a row with `version = epoch-ms`; reads take `argMax(value, version)` where `is_deleted=0`; deletes insert a tombstone; bulk LY/LLY re-seeds use atomic `ALTER TABLE … REPLACE PARTITION … FROM staging`. A guard tracks `mutations_used` and asserts it stays **0**. *Tradeoff:* history accumulates until background merges collapse duplicates (more storage, `FINAL`/`argMax` on read) — acceptable and it's exactly what powers undo/version-diff for free. *Impact:* converts the workload "from what ClickHouse is worst at to what it's fine at"; **`mutations_used = 0` at 1× and 10×** with correct read-after-write **[DESIGN/verified property]**. *Evidence:* `db_architecture_poc/domain/ch_planning_schema.sql`, `connectors/clickhouse.py`, `results/team_poc_results.json`, `docs/06`/`07`. *Honesty:* the *latency* ms in the PoC are mock; the *zero-mutation* property is the real, load-bearing result.

### D3 — Tenant-unified schema at the derived grain
> **Standardized a tenant-unified schema at the derived (cube) grain — one common `plan_cube` partitioned by tenant (Postgres `LIST(tenant)`; ClickHouse `(tenant, l1, fiscal_week)`) — so one codebase, query set and stored procedures serve every client with no per-tenant tables.**

**Backing.** *Why:* the legacy product forks a separate DB (and schema drift) per tenant, multiplying maintenance. *How:* define the cube grain once (`cluster × class × fiscal_week`), key every table by `tenant`, create one partition per tenant on onboarding; the tenant-parameterized cube-build SQL is identical across clients. *Tradeoff:* per-tenant *physical* isolation (separate Postgres DB + BigQuery project) is retained for security/blast-radius; "unified" is a **schema/codebase standard at the derived level**, not one shared physical instance. *Impact:* same queries/procedures everywhere → far less per-client code; onboarding a tenant = add a partition. *Evidence:* `domain/planning_schema.sql`, `domain/ch_planning_schema.sql`, `docs/06` R1.

### D4 — Cube + DuckDB pivot accelerator
> **Built a pre-aggregated planning cube plus an in-process DuckDB pivot accelerator so cross-tab pivots read a small columnar cube slice instead of raw fact tables, keeping pivots interactive as the cube scaled 1×→100× in the benchmark.**

**Backing.** *Why:* "pivot in the blink of an eye" over raw granular tables means re-scanning huge facts on every drag. *How:* materialize the cube in BigQuery, hydrate the plan's slice into an embedded DuckDB (Arrow), run native `PIVOT … USING sum() GROUP BY`; commit deltas back to Postgres. *Tradeoff:* the cube must be rebuilt/refreshed (staleness vs. speed) — acceptable for a planning cadence. *Impact:* pivot cost tracks the *cube slice* size, not the fact table. *Evidence:* `services/{cube_builder,pivot_service}.py`, `connectors/duckdb_engine.py`, `results/benchmark_results.json`. *Honesty:* the ms are mock/indicative — frame as "kept pivots interactive as the cube scaled."

## 2.4 Cost / performance (mostly REAL audit numbers)

### P1 — BigQuery cost program
> **Cut recurring BigQuery scan cost by up to ~280× (2.9 TiB → 3.3 GiB per query) by routing hierarchy reads to a clustered copy (~3×), materializing a store×category×week rollup (~280×; ~$8 one-time + ~$0.008/day), and enforcing partition pruning — after catching a single `SELECT *` query billing 38.8 TiB ($327) to return 2 rows.**

**Backing.** *Why:* BigQuery bills by **bytes scanned**; the hot recurring read rescanned the raw ~2.9 TiB fact. *How:* three levers — (1) read the clustered `_assort` copy, (2) build a narrow store×cat×week rollup, (3) require a date/partition predicate + kill `SELECT *`. *Tradeoff:* a rollup adds a build job + refresh; trivially paid back (~$8 once). *Impact:* ~3× → ~74× (with category pruning) → ~280×/~880× (rollup) fewer bytes **[REAL, live audit]**. *Evidence:* `benchmark/cost_model.py`, `docs/07` F2–F5. *Honesty:* these are **real** measured scan sizes/costs — defend them.

### P2 — BigQuery cost guard
> **Shipped a dependency-free "cost guard" in the query path that rejects `SELECT *` and un-dated scans and auto-routes raw-fact reads to the clustered copy — codifying the savings as a guardrail so future queries can't silently regress.**

**Backing.** *Why:* one-off fixes rot; the leak recurs. *How:* a small linter around query execution (`bq_cost_guard`/`connectors/bigquery.py`) with knobs `FORBID_SELECT_STAR` / `REQUIRE_DATE_FILTER` / `CLUSTERED_FACT`. *Tradeoff:* a few legitimate queries need annotation to pass — worth it. *Impact:* makes the ~3× routing automatic and the biggest leak impossible. *Evidence:* `connectors/bigquery.py`, `services/bq_cost_guard.py`. *Honesty:* real mechanism; framed as guardrail.

### P3 — Postgres write correctness & perf
> **Hardened the planning writes — wrapped multi-table saves in a single ACID transaction (eliminating ~88% orphaned optimizer rows), replaced N+1 per-row `jsonb_set` update loops with a set-based `UPDATE … FROM json_to_recordset`, and added the missing cascade-delete FK indexes.**

**Backing.** *Why:* non-atomic multi-statement saves left orphans; per-row loops on a 138-column partitioned table are the top write hotspot; un-indexed cascade FKs seq-scan on every plan delete. *How:* one transaction/array per save; one set-based statement per plan; three one-line `CREATE INDEX`. *Tradeoff:* minimal — pure win. *Impact:* correctness (no orphans) + far fewer statements per save. *Evidence:* the performance-findings doc (§2, §3.2); `docs/07` F12/F14. *Honesty:* orphan % is a **real** audit fact; the write rewrite is a recommended fix you designed.
